# 一貫性のある親しみやすいヘルプページ作成ガイド

## 🎯 目標

- **一貫性**: 統一されたデザイン・文体・構成
- **正確性**: 実際の機能と100%一致した内容
- **親しみやすさ**: ITに詳しくない教育現場の先生方でも理解できる
- **直感性**: 必要な情報に素早くアクセスできる構成

## 📋 現状の問題分析

### タイトル不整合（3層の齟齬）

- **実際のPageHeader**: 「模範解答画像の管理」
- **usePageHelpマッピング**: 「模範解答アップロード」
- **ヘルプページ内容**: 「採点領域作成 - 完全ガイド」

### 文体・表現の問題

- 「完全ガイド」「ベストプラクティス」など硬い専門用語
- 長い説明文で読む気を失わせる構成
- 実装と異なる機能説明（TIFFサポートの誤記載等）

### 機能説明の不正確性

- ヘルプ内容が古い実装に基づいている
- 複雑な機能の変更が反映されていない
- 実際のUI・操作フローとの乖離

## 🏗️ 体系的アプローチ

### STEP 1: ヘルプページ作成ガイドライン策定

#### タイトル規則

- **基準**: 実際のPageHeaderタイトルを必ず確認して使用
- **形式**: 「[実際のタイトル] - 使い方」で統一
- **例**: 「模範解答画像の管理 - 使い方」

#### 文体ガイドライン

- **敬語**: 「〜しましょう」「〜してください」の親しみやすい表現
- **専門用語の日常語化**:
  - DPI → 画質
  - ベストプラクティス → 上手に使うコツ
  - 効率的な処理 → まとめて処理
  - グレースケール → 白黒
- **文章の長さ**: 1文50文字以内の簡潔な表現
- **段落**: 3行以内で区切る

#### 構成テンプレート

```
1. 基本の使い方 (必須・最重要)
2. [機能固有セクション] (横並び対応)
3. 困ったときは (必須・実用的)
```

### STEP 2: 詳細な実装調査プロセス

> **重要**: ヘルプページの正確性は、実装の詳細調査に完全に依存します。推測や古い情報に基づく内容は絶対に避けてください。

#### 必須調査項目

1. **実際のPageHeaderタイトル確認**

   ```bash
   grep -r "PageHeader.*title" app/projects/[projectId]/[page]/
   ```

2. **主要コンポーネントの機能分析**
   - メインページコンポーネント
   - 関連するフック・ユーティリティ
   - 型定義ファイル

3. **ユーザーの実際の操作フロー把握**
   - どのボタンを押すのか
   - どのような順序で操作するのか
   - どのような制限・エラーがあるのか

4. **キーボードショートカット確認**
   - 設定可能なショートカット
   - デフォルトのキー配置
   - macOS対応状況

5. **制限事項・エラーケースの特定**
   - ファイルサイズ制限
   - ファイル形式制限
   - 同時処理数制限
   - エラーメッセージの内容

#### 調査の実施方法

```bash
# 1. ページタイトルの確認
grep -rn "title=" app/projects/[projectId]/[page]/

# 2. メインコンポーネントの詳細読み取り
read [メインページファイル]
read [関連コンポーネントファイル]

# 3. 機能固有のフック・ユーティリティの確認
glob hooks/*[page]*
glob utils/*[page]*
glob types/*[page]*

# 4. 制限事項・バリデーションの確認
grep -r "maxFileSize\|validation\|limit" components/projects/[page]/
```

### STEP 3: デザインパターンの標準化

#### レスポンシブ設計

- **タブレット以上**: `lg:grid-cols-2`
- **大画面**: `xl:grid-cols-2`
- **情報密度の最適化**: 重要な情報を画面幅に応じて効率配置

#### 視覚的一貫性

- **アイコン**: Lucide Reactで統一
- **カラーコード**:
  - blue-600 (情報)
  - green-600 (成功・次ステップ)
  - yellow-600 (注意・ヒント)
  - red-600 (警告・エラー)
- **TipItemタイプ**: info, warning, success の3種類を適切に使い分け

#### コンポーネント使用パターン

```tsx
// 基本構成
<HelpSection icon={<Icon />} title="タイトル">
  <StepItem number={1} title="ステップ" description="説明" />
  <TipItem type="info">ヒント内容</TipItem>
</HelpSection>

// 横並びレイアウト
<div className="grid lg:grid-cols-2 gap-6">
  <HelpSection>...</HelpSection>
  <HelpSection>...</HelpSection>
</div>
```

## 📝 実装調査の重要性

### なぜ詳細調査が必要か

1. **機能の複雑性**: 教育用採点ツールは高度な機能を持つため、表面的な理解では不正確な説明になる
2. **継続的な改善**: 開発が継続中のため、古い情報と実装が乖離している可能性が高い
3. **ユーザー体験**: 実際の操作と異なる説明は、ユーザーの混乱と作業効率低下を招く

### 調査不足のリスク

- **機能誤解**: ユーザーが期待する動作と異なる結果
- **操作エラー**: 間違った手順による作業失敗
- **信頼性低下**: 不正確な情報によるツール全体への不信

### 調査徹底のメリット

- **正確性保証**: 実装と100%一致した情報提供
- **効率向上**: 正しい操作手順による作業時間短縮
- **ユーザー満足度**: 信頼できる情報による安心感
