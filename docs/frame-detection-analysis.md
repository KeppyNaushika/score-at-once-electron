# 採点枠自動検出 — アルゴリズム分析・最適化レポート

> 作成日: 2026-03-24
> 対象: `src/components/exams/02-template/utils/frameDetector.ts`, `frameDetector.worker.ts`

## 1. 背景

精度改善コミット（`e35a9a60`）以降、採点枠自動検出が重くなりUIがブロッキングされる問題が発生。
原因調査と最適化を実施し、あわせて単元テスト形式の答案での検出精度を検証した。

## 2. 実施した最適化

### 2.1 パフォーマンス改善

| 最適化                 | 内容                                                 | 効果                               |
| ---------------------- | ---------------------------------------------------- | ---------------------------------- |
| ダウンサンプリング     | 長辺2000px制限。Canvas `drawImage`で縮小後に処理     | 52Mpx→2.8Mpx（最大画像で18倍削減） |
| スケール対応パラメータ | tolerance値を `refDimension / 2000` で比例調整       | 解像度非依存の一貫した検出挙動     |
| 辺マージン除外         | 画像端1.5%以内の線を除外                             | スキャナーの影・ページ枠の偽線除去 |
| 交差マップ方式         | `buildRectsFromLines`をO(H²×V²)→O(H×V + H²×K²)に置換 | 線数50×30で約10倍高速化            |
| 線数上限               | 矩形構築に使う線を長さ順で上位100本に制限            | 組み合わせ爆発の防止               |
| Web Worker化           | 計算処理を専用Workerに委譲                           | UIブロッキング完全解消             |

### 2.2 パフォーマンス計測結果（全33枚の実模範解答画像）

| 画像サイズ          | 最適化前（推定）   | 最適化後          |
| ------------------- | ------------------ | ----------------- |
| 6070×8598（最大）   | 3-10秒、UIフリーズ | ~90ms（Worker内） |
| 2382×3368           | 1-3秒、UIフリーズ  | ~80ms             |
| 1190×1683（A4標準） | 200-800ms          | ~55ms             |

## 3. 精度検証（VLMによる目視確認）

全33枚の模範解答画像に対し、検出結果を画像上にオーバーレイ描画し、VLM（Vision Language Model）で目視検証を実施。

### 3.1 検出が良好な画像の特徴

- **太い罫線で囲まれた解答欄**（表形式、グリッド形式）
- **テキストが少ない**ページ（白紙に近い答案用紙）
- 解答欄が**規則的に配置**されている（同じx座標に左辺が揃う）

代表例: 罫線が明確な解答欄付きテスト、マークシート、調査書形式

### 3.2 検出が不十分な画像の特徴

- **模範解答（文字）が記入済み**の答案
- **密なテキスト**が解答欄の周囲にある
- 解答枠の罫線が**薄い/細い**

代表例: 模範解答記入済みの単元テスト（複数教科で確認）

## 4. 根本原因分析

### 4.1 ピクセルレベル分析

検出不良画像と検出良好画像のピクセル分布を比較した結果、**二値化閾値は適切**であることを確認。
枠線のピクセルは正しく「暗」として検出されており、閾値の問題ではない。

### 4.2 線検出分析

| 画像タイプ          | 水平線数 | 短い線(<3%幅) | 解答枠サイズの線(8-25%) | 検出結果 |
| ------------------- | -------- | ------------- | ----------------------- | -------- |
| テスト用紙A（良好） | 32本     | 1本           | 24本                    | 8-10個   |
| 単元テストB（不良） | 105本    | 53本          | 7本                     | 2個      |
| 単元テストC（不良） | 202本    | 90本          | 45本                    | 14個     |

### 4.3 特定された3つの原因

#### 原因1: テキストの文字画が「水平線」として大量に誤検出される

アルゴリズムは黒いピクセルの連続を全て「線」として扱う。
日本語の文字（特に横画の多い漢字）や数式は、行方向に連続する暗ピクセルを生成し、「水平線」として検出される。

**人間の目はテキストと罫線を意味的に区別できるが、アルゴリズムは区別できない。**

密なテキスト（模範解答記入済み）の場合、テキスト由来の短い偽線が大量に発生し、線数上限100本の枠内で実際の枠線が押し出される。

#### 原因2: 解答枠の垂直辺が短すぎて交差条件を満たさない

交差分析の結果、解答枠の垂直辺（左辺・右辺）は高さの2-3%程度（40-60px）しかない。
この短い垂直線は、上辺の水平線と下辺の水平線の**片方としか交差しない**ケースが多い。

矩形の形成には上辺・下辺・左辺・右辺の4本全てが相互に交差する必要があるが、
垂直線が短いと「上辺とは交差するが下辺には届かない」状態になり、矩形が形成されない。

`lineExtension`パラメータで線を延長すると改善するケースがあるが（1→7個に増加する画像あり）、
同時に過検出が悪化する画像もある（19→72個に増加する画像あり）ため、デフォルト値は0のまま据え置いた。

#### 原因3: 模範解答画像に正解が記入されている

模範解答（模範解答）には正解の文字が記入されており、これが原因1のテキストノイズを増幅する。
白紙の答案用紙であれば罫線のみが検出対象となり、精度が大幅に向上する。

| 状態             | 水平線数  | 検出精度 |
| ---------------- | --------- | -------- |
| 白紙に近い答案   | 30-90本   | 良好     |
| 模範解答記入済み | 100-700本 | 不良     |

## 5. `lineExtension`パラメータの効果検証

`lineExtension`を0〜20の範囲で変化させ、検出数の変化を計測。

### 感度3（デフォルト）での結果

| 画像タイプ          | ext=0 | ext=5 | ext=10 | ext=15 | ext=20 |
| ------------------- | ----- | ----- | ------ | ------ | ------ |
| 単元テストB（不良） | 1     | 3     | 3      | **7**  | 7      |
| 単元テストD（不良） | 1     | 1     | 2      | **6**  | 16     |
| テスト用紙A（良好） | 10    | 10    | 10     | **10** | 10     |

検出良好な画像は`lineExtension`の影響を受けない（線が既に十分に交差しているため）。
検出不良な画像はext=15で改善するが、一部の画像で過検出が発生するトレードオフがある。

**ユーザーへの推奨**: デフォルト0で使用し、検出が不十分な場合はUIスライダーで10-15に調整。

## 6. アーキテクチャ変更

### 6.1 変更前

```
frameDetector.ts (メインスレッド)
  └── 画像ロード → グレースケール → 二値化 → 膨張 → 線検出 → 矩形構築 → フィルタリング
      （全て同期処理、UIブロッキング）
```

### 6.2 変更後

```
frameDetector.ts (メインスレッド — オーケストレーター)
  ├── 画像ロード＆ダウンサンプリング (DOM操作、メインスレッド)
  ├── ImageDataのArrayBufferをWorkerに転送 (transferable, コピーコストゼロ)
  └── 結果にIDを付与して返却

frameDetector.worker.ts (Web Worker — バックグラウンド)
  └── グレースケール → 二値化 → 膨張 → 線検出 → 辺マージン除外 → 線数制限 → 線延長 → 矩形構築 → フィルタリング
      （非同期処理、UIブロッキングなし）
```

### 6.3 矩形構築アルゴリズムの変更

**変更前（O(H²×V²) ブルートフォース）:**

```
for each pair of horizontal lines (i, j):
  for each pair of vertical lines (k, l):
    if all 4 corners intersect: → rectangle
```

**変更後（交差マップ方式）:**

```
Phase 1: 各水平線が交差する垂直線のインデックスリストを事前計算 — O(H×V)
Phase 2: 水平線ペアごとに共通垂直線をソート済みマージで取得 — O(H²×K)
         共通垂直線ペアから矩形を構築 — O(H²×K²), K << V
```

## 7. 今後の改善候補

### 7.1 モルフォロジー演算による線抽出（中優先度）

横長カーネル（1×40）と縦長カーネル（40×1）でopening（収縮→膨張）を行うと、
テキスト由来の短い線が除去され、構造的な罫線のみが残る。
文書画像解析の標準的な手法で、テキストノイズ問題の根本解決になりうる。

### 7.2 白紙テンプレートの別途アップロード（低優先度）

模範解答画像とは別に、白紙の答案用紙を枠検出専用にアップロードする機能。
模範解答記入によるノイズ問題を運用レベルで回避できる。

### 7.3 膨張処理のセパラブル化（低優先度）

3×3カーネルを水平1×3 + 垂直3×1の2パスに分離。
ダウンサンプリング後は効果が限定的（10-30ms → 7-20ms程度）。
