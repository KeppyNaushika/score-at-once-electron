## 段階23 — 小計グループの更新を差分書き込みへ直す

**済**（2026-08-20・`ed59222f`）。id で突き合わせて「外れたものだけ消し、変わったものだけ
更新し、増えたものだけ作る」形にした。検査6本を足し、**6本とも旧実装で落ちることを実測**
してある。新規項目の id は **DB が振る**（画面側の `id` は既存行では DB の id、新規行では
`temp-${Date.now()}` という合成 id という二重の意味を持っており、そのまま渡せる形では
なかった。ついでに同じミリ秒で衝突する React key も直した）。

**残した制限が1つある。** `Subtotal` は `@@unique([subtotalGroupId, name])` を持つので、
**2つの項目が名前を互いに入れ替える保存だけ通らない**（途中で重複してトランザクションが
落ちる）。旧実装は全消ししてから作るので通っていた。真の入れ替えを通すには一時的な仮名を
書く必要があり、同期の変更履歴にゴミが流れるのでやっていない。**そもそもこの `@@unique` は
`name`（uuid でない値）を鍵にしており、段階29 で整理する規約に反している** — 撤去の可否は
段階30 で判断する。

**いま実際にデータが消えている。** 見つかったのは 2026-08-20、規約に沿って計画を見直す
過程で。

### 症状

**小計点グループの名前を1文字直して保存すると、04 で設定した設問の割り当てが全部消える。**
その小計を参照している成績のデータソースも消える。割り当て直しても、`Subtotal` の id が
変わっているので元には戻らない。

### 機構

`electron-src/lib/prisma/subtotalGroup.ts:97`

```ts
await tx.subtotal.deleteMany({ where: { subtotalGroupId: id } }) // ← 全部消す
return await tx.subtotalGroup.update({
  data: { name: data.name, subtotals: { create: data.subtotals } }, // ← 作り直す
})
```

`Subtotal` には**カスケードする子が2つ**ある。

```prisma
model Subtotal {
  cropSubtotals    CropSubtotal[]      // onDelete: Cascade
  gradeDataSources GradeDataSource[]   // onDelete: Cascade
}
```

同期にも毎回 tombstone と新しい id が流れる。

### 棚卸し（2026-08-20）

`electron-src/lib/` の全書き込みから「`deleteMany` と `create` が同居するもの」を機械で
拾うと **18件**。うち**消される行に孫がいるのは `updateSubtotalGroup` だけ**だった
（他は葉＝タグの紐付け・選択肢・境界・刻みなど）。

**同じ形は既に潰されている。** `updateCourseworkItem` のコメントが証拠になっている。

> かつてここが刻みの配列を受け取り `deleteMany` → `create` していたため、項目名を1文字
> 直すだけで全行の id が振り直されていた。

段階11（04 の割り当て）・段階17（タグの紐付け）でも同じ形を潰した。**小計グループだけが
残っていた。**

### 直し方

`setAsbDefinitionTags` と同じ形にする。**外れたものだけ消し、変わったものだけ更新し、
増えたものだけ作る。**

- **突き合わせは id で。** `Subtotal` は `@@unique([subtotalGroupId, name])` を持つが、
  名前で突き合わせると「並べ替えと改名が同時に来たとき」に別物として扱ってしまう。
  画面側の `SubtotalFormData` は既に `id` を持っている
- 触った行が無ければ何も書かない

### 検査

- **グループ名を変えても、設問の割り当て（`CropSubtotal`）が残る**
- 小計項目を1つ消しても、残った項目の id が変わらない
- 小計項目を並べ替えても、id が変わらない

ガードは外すと実際に落ちることを確認してから採用する。

### 途中で出た、まだ決めていないもの（2026-08-20）

**「sqlite-nas-sync の制約で `id` 以外の unique を置けない」と書いた箇所が13ある。**
言い方が違っている。正しくは **「uuid 以外を unique にしない」** で、理由は衝突の*意味*が
変わるからである。

- **uuid で構成された unique**（`(examId, studentId)` など）— 2端末が同じ値を作るのは
  「同じものを2回作った」とき。**畳んで正しい**
- **序数や名前を含む unique**（`(examId, pageNumber)` など）— 端末Aの3ページ目と端末Bの
  3ページ目は**別の行**。同じ値になるのは偶然で、**畳むと別物が1つに潰れる**

13箇所は2種類に分かれる。`06-student-answers/types.ts:11` や `pdfExport.ts:154` は
`pageNumber` の話なので**結論は正しく、言い方だけが違う**。`questionScore.ts:218`
（`examStudentId, cropRegionId, userId`）や `schema-relation-audit.md:93`（`examPageId`）は
**全部 uuid** なので、理由の書き方が違う。

この誤解は設計を実際に動かしている（「unique が無いので `upsert()` が使えず `findFirst`
＋分岐を手書き」「`@unique` を足すのが最短だが方針に反するので迂回した」）。ただし
**全部 uuid だからといって無条件に張ってよいわけでもない** — 子を持つ表では、段階20 が
入るまで勝った端末が詰まる。

**判断待ち。** 立てるなら「言い方を揃える」までを1段とし、**実際に張るかどうかは段階20 の
後**（詰まりが直るまで新しい unique は増やせない）。

## 段階21 — 採点行は、注釈を書くときに main が用意する

**済**（2026-08-21・`e4962b99`）。`ensureQuestionScore` の IPC チャンネル・preload の口・
renderer の mutation を撤去した（renderer から呼べる限り「表示したら書き込む」へ戻れる）。
呼び出し元ゼロで死んでいた `initializeScoringRecords` も撤去。検査7本。**旧版が量産した
空行の掃海はしていない**（破壊的操作なので別途・要許可）。

R7/R8 の指摘 #2 の2段目。**表示しただけで DB に行を作るのをやめる。**

### なぜ

`unscored` の行は情報を1ビットも持たない。**行の不在が既に全経路で未採点として読まれて
いる**からで、確定リゾルバ・成績算出（試験合計／設問単体）・Excel・個人成績表・平均行・
SP分析のどれも、行の有無と `unscored` を区別しない（全数調査は
[branch-review-findings.md](./branch-review-findings.md) #2）。

にもかかわらず作っている理由は1つだけ — **`DrawingAnnotation.questionScoreId` が必須のFK**で、
renderer が描く前に `questionScoreId` を必要とすること。**置き場所が要るという都合が、
「表示したら書き込む」という振る舞いになっている。**

副作用として、設問をめくるだけで空行が量産される（40人×30問で1教員あたり1200行）。行が
増えるほど[段階20 の衝突](./sync-secondary-unique-hazard.md)の機会も増える。

### 形

```
いま:     画面が先に行を作る → その id を持って描く → 注釈を保存する
これから: 画面は描く → 保存で「答案＋設問＋採点者」を送る
          → main が必要なら行を用意して、注釈をぶら下げる
```

**IPC は意図を運ぶ**（「この答案のこの設問に、この注釈を描いた」）。置き場所の都合は main
の内側へ入る。

- 注釈の保存・取得の口から `questionScoreId` を外し、`examStudentId` / `cropRegionId` /
  `userId` を受ける
- renderer のキャンバス層が `questionScoreId` を前提に組まれているので、そこを解く
- `status:"unscored"` を書いてよいのは、利用者が明示的に「未採点に戻す」を選んだときだけ

### 前提

**#2 の1段目（`setQuestionScore` / `ensureQuestionScore` への分割）を先に入れる。** あちらは
数行で採点消失を止める。この段階はそのあと、空行を作らない形へ進める。

### 併せて片付くもの

- `initializeScoringRecords`（`prisma/scoringInitializer.ts`）は呼び出し元ゼロで死んでいる。
  撤去する
- **リゾルバの `unscored` 除外は残す。** 注釈だけ付けて採点はまだ、という状態を表すのに
  `unscored` の行は今後も要る。除外はその不変条件の表明であって、掃き残しへの応急処置では
  ない。ただしコメントの理由を書き換え、型で守る（指摘 #16）

### やらないこと

- **旧版が量産した空行の掃海。** やる価値はあるが破壊的操作なので別途・要許可。条件は
  「`unscored` かつ 注釈が無く かつ `ScoreDecision.sourceQuestionScoreId` から参照されて
  いない」（後者は FK ではない生の文字列なので、消すとぶら下がりが残る）
- **アーカイブ側での間引き。** 「アーカイブは正本・存在について忠実復元」の裁定に反する

## 段階26 — 消す前に数え直して中止する（全ての削除）

削除の確認は「消すと何を巻き添えにするか」を数えて見せる。**数え終わってから利用者が押す
までの間に、他の教員が書き足す窓**が残っている。

**「消す前に数え直して、増えていたら中止する」を共通の作法にする**（OWNER 決定）。答案の
削除だけに入れると一貫しないため。

### いまどうなっているか

答案の削除は**すでにトランザクションの中で数え直している**
（`deleteStudentAnswer` → `countStudentAnswerScoreData`）。ただし返り値（表示用）に使うだけで、
**中止の判断には使っていない**。繋げば塞がる。

### やること

1. 削除の確認を持つ経路を数える（答案・学級・生徒・試験・資料）
2. **共通の形を1つ決める** — 「利用者に見せた件数」を削除の要求に添え、main が消す直前に
   数え直し、食い違えば中止して差分を返す
3. 画面は「他の教員が採点しました。もう一度確認してください」と伝えて数え直す

### 注意

- **数える定義を、見せたものと揃える。** `deleteStudentAnswer` のコメントが指摘している
  とおり、削除自体は `unscored` の初期化行も含めて全て消すので**行数とは一致しない**。
  比べるのは「利用者から見た採点実績」でなければならない
- 窓は縮むが消えない（数え直しと削除は同じトランザクションに入れる）

## 段階20 — 競合で負けた行の子を、ライブラリ側で引き取る

**実装済み・指摘対応中**（2026-08-21）。`~/dev/sqlite-nas-sync` に3本（`a430d9d` v0.14.0 /
`59b3102` v0.15.0 / `046d592`）。テスト123本緑。**publish はしていない。**

3台目の穴を実測で見つけて2度直している。(1) 畳み先をローカルの `_id_merge` にだけ持つと、
衝突を経験しなかった端末は何も導けず、tombstone を適用した瞬間に自分の子を失い、その削除が
伝播して**他端末で付け替え済みの子まで殺す**。畳み先を `_tombstone.mergedInto` に載せて
伝播に乗せた。(2) `local_wins` 側は DELETE が起きず changelog に載らないので、畳み先が
フルマージ経路でしか回らない。隙間ができるのは保持期間を超えて離脱した端末だけなので、
**行儀よく同期している端末ほど受け取らない**という逆転になっていた。`_changelog` へ
DELETE を手書きして差分経路にも乗せた。

**そのうえで独立のレビューが7件の指摘を出しており、未着手のまま別セッションへ引き継いだ。**
最重要は「手書きした changelog の DELETE が生まれた時点で期限切れになりうる」（
`recordTombstoneMerge` の upsert が `deletedAt` を更新しないため、既存 tombstone があると
古い時刻で入り、同じ `performSync` の `cleanupChangelog` がアップロード前に消す。以後
`alreadyRecorded` が真で二度と書かれない）。**これが成立すると (2) の修正が無効化される。**
呼び出し元がコードで裏を取った。残り6件は読んだだけで未実測。

**作業先はこのリポジトリではない**（`~/dev/sqlite-nas-sync`）。それでもここへ置くのは、
協調採点が成り立つ前提そのものだからで、宙に浮かせると誰も拾わない。

### 何が起きているか

2端末が同じものを独立に作ると、中身は同じで id だけ違う行が2つできる。ライブラリは
これを LWW で1行へ畳む（`conflict.ts:207`）。**畳み方が「負けた行を消す」なので、負けた
行に子がぶら下がっていると巻き添えになる。**

帰結は2つあり、どちらも**画面に何も出ない**。

1. **負けた側の子データが消える。** 2人の教員が同じ生徒を同じ試験へ加えて採点すると、
   **片方の採点がどこにも残らない**（負けた `ExamStudent` の削除が `QuestionScore` へ
   カスケードする）
2. **同期がその相手から永久に止まる。** 勝った端末は相手の子を置く場所が無く外部キー
   違反を出す。適用ループは相手1人ぶんが1トランザクションで、読んだ位置も巻き戻るので、
   次回も同じ所で落ちる。**無関係なテーブルの変更も以後いっさい届かない**

**実測済み**（3回試して `clientsSynced=0`、無関係な行も届かず）。詳細・再現手順・該当10
モデルは [sync-secondary-unique-hazard.md](./sync-secondary-unique-hazard.md)。

### 直し方

**負けた行を消す前に、負けた行を指している子を勝った行へ付け替える。**

付け替え先はライブラリが自力で辿れる。SQLite が `PRAGMA foreign_key_list` で「どの表が
この表を指しているか」を答えるので、**スキーマを知らなくてよい**。

これで上の2つが同時に片付く。詰まらなくなるのはその結果であって、目的ではない。

### 境界（できないこと）

- **負けた行の属性はマージできない。** 列の意味を知らないため、勝った行が総取りする。
  既知の穴として据え置く（`ExamSubtotalGroup` の2つのフラグが実例）
- **付け替えた子が子自身の制約にぶつかる場合**の扱いは未決。同じ LWW をもう一段回すのか、
  別に扱うのか
- **孫は動かさない**（子を指したままでよい）。要確認

### アプリ側で避ける案は採らない

「1:1 の表は id を親から決めれば衝突自体が起きない」は**実測で効くと確認したが採らない**
（OWNER 判断・2026-08-19）。id を内容から導出する形は 2026-08-03 の PR #1150 で3系統
（合成id・親の id 流用・uuidv5）すべて撤去され、`uuidIdCoverage.test.ts` が禁じている。
**方針には独立した根拠がある** — id が同一性を持つと、消して作り直した行が tombstone に
潰されて復活しない、という逆向きの事故が起きる（`20260803110000_unify_ids_to_uuidv4` の
冒頭に記載）。今回の実測はその根拠を崩していない。

### この修正が可能にすること

**FK を張れなかった列に張れるようになる。** 「親がまだ届いていない子を保留して再試行する」
が入れば、読む順による FK 違反が解ける。対象は `ScoreDecision.sourceQuestionScoreId` と
`ReturnSnapshot.capturedByUserId` の2件 → **段階22**。

### 併せて直すもの

**「LWW が畳む」と書いてある説明文に、「敗者に子がいない場合に限る」を足す。**
`uuidIdCoverage.test.ts` の冒頭と `schema.prisma` の3箇所（`:210` / `:283` / `:895`）。
いまの文面は次に読む人へ「ライブラリが全部畳んでくれる」と誤って伝え続ける。
**これは実装より先に済ませる。**

| `ReturnSnapshot.capturedByUserId`     | **張る**                       | `Cascade`  |
| `AuditLog.userId`                     | 張らない（削除後もログを残す） | —          |

`capturedByUserId` は **`Cascade`**（OWNER 決定・2026-08-19）。利用者を消したら、その人が

### `ScoreDecision.sourceQuestionScoreId` は列ごと消す（OWNER 決定・2026-08-19）

FK の張り方を論じる前に、**そもそもこの列が要らない**。

> 誰の採点結果を採用しているのかは**不明**である。2人が同じ「正答」を付けていたら、
> どちらを採用したのか、両方なのか、決まらない。**保存すべきは採点結果であって、
> 由来ではない。**

`verdict` / `score` / `comment` / `decidedByUserId` で確定は完結している。

**UI も同じ根で変わる。** いまの `ScoreDecisionForm` は「**人を選ぶ**」形で、同じ結果を出した
2人のどちらか一方を選ばされる（選んだ id に意味が無い）。これからは「**結果を選ぶ**」——
判定と点でまとめ、その結果を出した人たちは横に並ぶだけで選択の対象にしない。**同じ結果の人を

## 段階34 — 書き込みの引数から optional と死んだ列を無くす

**見本は `UpdateQuestionScoreData`**（`electron-src/lib/prisma/questionScore.ts`）。

```ts
export interface UpdateQuestionScoreData {
  partialScore?: number // 省略すると null が書かれる（＝消える）
  status?: ScoringStatus // 省略すると触らない          ← 意味が逆
  comment?: string // QuestionScore に comment 列は存在しない
  version?: number // version 列はどのモデルにも存在しない
}
```

**同じ袋の中で、省略の意味が列ごとに逆**であり、4つのうち2つは**存在しない列**を指している。

**「楽観的ロック」は実装されたことがない。** `version` 列がどのモデルにも無く、
`expectedVersion` は一度も比較されない。実際にやっているのは「その行がまだ在るか」の確認
だけで、それは直後の `before` の取得が同じことをしている（**同じ `findUnique` を2回**）。
返している `SCORE_TARGET_DELETED` 自体は有用なので、**名前と説明を実体に合わせる**。

> **`version` / `expectedVersion` は削除する**（OWNER 決定・2026-08-21）。renderer は
> 一度も渡しておらず、IPC まで通っているだけの死んだ経路である。スキーマ変更は伴わない
> （足そうとして足されなかった列なので、消す列が無い）。重複した `findUnique` も1回にする。

### 割るのではなく、必須にする

「1変更＝1Prisma・1IPC・1query」の**「1変更」は列ではなく、利用者から見た1つの決定**である。
採点の場合それは「このマスの採点結果はこれだ」であり、`(status, partialScore)` の組で1つ。
正答にするときも `partialScore` に `null` を指定することになるので、**割る必要はない**。

```ts
{
  status: ScoringStatus
  partialScore: number | null
} // 両方必須。省略なし
```

**optional が無ければ、省略の意味を考える必要がない。** 「省略＝消す」の罠も、列ごとに
意味が逆になることも、渡しても何も起きない列も、まとめて消える。

### 併せて片付くもの

- **union があるのに生 `string` で受けている書き込みの口が13〜14箇所**（`scoreDecision.ts` の
  `verdict`、`questionScore.ts`、`compoundAnswer.ts`、`returnSnapshot.ts`、`pdfExport.ts`、
  `userScoringStatusColor.ts`、`examHandlers.ts`、`cropRegionHandlers.ts`、
  `drawingAnnotation.ts`、`masterAnswer.ts`、`studentAnswer/crud.ts`、`gradeHandlers.ts`）。
  `UpdateQuestionScoreData` は**7値をその場に手書き**しており、CLAUDE.md が名指しで禁じた
  「union 手書き重複」（過去に hold/pending のドリフトを生んだ原因）にあたる
- **土台を Prisma の入力型へ。** `Prisma.XUncheckedCreateInput` / `UncheckedUpdateInput` が
  書き込みの形を既に生成している（`generated/` は `.gitignore` 済みの自動生成）。手写しの
  列を並べず、**① DB が決める列（`id` / `createdAt` / `updatedAt` / `decidedAt`）を除去し、
  ② Decimal と union だけを注入する**
- **`?? null` の棚卸し。** `electron-src/lib/prisma` に139箇所。作成の枝では無害だが、
  `update` の枝にあると「省略」を「NULL にしろ」へ変換する。**何件が `update` 側かは
  まだ数えていない**

**いま事故は出ていない。** `upsertScoreDecision` の呼び出し元は確定パネル1つで、そこは

**Prisma の流儀（省略＝触らない）と逆**であることで、2人目がそちらの流儀で書くと消える。

## 段階53 — 関門が保証している型を、そのまま配る

`useAuth` の使い手は **31 → 3**（`login/page.tsx`・`AuthGate`・`Navigation`）。

### 出てきたもの

## 段階38 — 原稿用紙の upsert が renderer の id を捨てるのを直す（R10 指摘1）

1. **`deleteManuscriptPaper` が失敗したあと** — reducer は先に木から落とすので、IPC が

2. **別ウィンドウ・別端末が先に作った** — 読み込み後に相手が作れば、こちらの木は知らない

- `ManuscriptPaperSettings.tsx:152` の `addCharGuide(manuscriptPaper.id, …)` は

**main が書いた行の id を返し、renderer が自分の木を直す**のが素直。`writeRow` の返りを

## 段階39 — migration をまたいで FK の設定が漏れるのを止める（R10 指摘2）

`migrationDeployer` は**1本の接続**で未適用ぶんを名前順に `db.exec(sql)` する
（`electron-src/lib/prisma/schema/migrationDeployer.ts:39,82`）。`PRAGMA foreign_keys` は
接続に紐づく状態なので、**あるファイルが最後に置いた値が、そのあと同じ起動で走る全ての
migration の初期状態になる。**

### これは1本の問題ではない

段階24 の migration は 71行で `OFF`、104行で `ON` に戻す。しかしこれは
**Prisma が生成する RedefineTables ブロックの定型**で、この形の migration が本リポジトリに
14本ある（`grep -rn 'PRAGMA foreign_keys' prisma/migrations/`）。
`20260704010000_rename_class_tables_to_classroom` は逆に `ON` で開いて `OFF` で閉じる。

つまり**どの migration も、自分が開始する時点の FK の状態を当てにできない。** 現状は
RedefineTables 系が自分で `OFF` を敷くので偶然かみ合っているが、これは規約ではなく偶然で、
`ALTER TABLE … RENAME TO` は逆に `ON` を要求する（子の FK 参照を書き換えさせるため。
`project_migration_rename_fk_gotcha` の実例）。

### 直し方

**1本を直すのではなく、deployer 側で括る。** 各 migration を流す前に既知の状態
（`PRAGMA foreign_keys=OFF`）へ戻す。そのうえで、`ON` を要求する migration は自分で
`ON` を敷く（いまもそうしている）。migration ファイル側は触らない — **歴史 migration は
編集禁止**であり、既に配られた DB では適用済みだから直しても届かない。

### 併せて直すもの

段階24 の migration の 68〜70行のコメントは `defer_foreign_keys=ON` が効いている前提で
書かれているが、**自動コミット実行では `defer_foreign_keys` は実質無効**（効いているのは
`foreign_keys=OFF` の方）。コメントを実態へ合わせる。ファイルの SQL 自体は変えない。

### 検査

空 DB へ全 migration を昇順適用したあと `PRAGMA foreign_key_check` が空であること、を
既存の検査に足す。いまの検査は各 migration が通ることしか見ていない。

## 段階43 — 枝問の原稿用紙の幅を通し、超過を入力で止める（R10 指摘3）

**OWNER 決定・2026-08-21。** 枝問にも小問と同じ機能を持たせる。マス目は
`基準行高 × 倍率` の正方形、**列数は任意の整数**。幅はそこから決まる。

### いまどうなっているか

**高さは既に伝わっていて、幅だけが伝わっていない。**

`buildSubGridLayout`（`gridBuilder.ts:178-184`）は、枝問を持つ小問の高さを
`gridTotalHeight(branchCells)` で**枝問の実測から積み上げ直している**。枝問が原稿用紙で
背を伸ばせば、親の小問もその分伸びる。ところが**幅にはこの積み上げが1本も無い**。

小問側は割り当ての前に幅を注入している（`computeLayout.ts:180-188`）。

```ts
const reqW =
  baseRowHeight * sub.heightMultiplier * sub.manuscriptPaper.columns + snw
return { ...sub, layoutWidth: String(reqW / horizontalAreaWidth) }
```

ただしこの書き換えには `sub.branchQuestions.length === 0` という条件が付いていて、
**枝問を持つ小問は除外されている**。枝問側の `buildBranchGridLayout`
（`gridBuilder.ts:200-213`）は高さだけを広げ、幅を触らない。描く側
（`lineRenderer.ts:300`）はマス目の幅で描くので、**割り当てと描画が食い違う**。
囲み枠の右端は `computeGridRowRightEdges` がグリッド比だけで出すため、マス目が大問の枠と
用紙の右端を突き抜ける。

### やること

1. **高さでやっていることを、幅でもやる。** 枝問それぞれの必要幅を出し、その最大値
   （＋枝番号の幅）を親の小問の必要幅として積み上げ、親の `layoutWidth` も書き換える。
   小問側の除外条件（`branchQuestions.length === 0`）はここで解ける
2. **列数に上限を置き、入力で止める**（下記）
3. ついでに `snw` / `reqW` を `subNumberWidth` / `requiredWidth` へ直す（命名規約）

### 幅の超過は許容しない（OWNER 決定）

段の幅から**列数の上限を算出し、入力をそこで止める**。上限は画面に出す
（「この段幅では最大12マス」）。段組み2段で20マスは A4 横幅に物理的に入らないので、
組版の途中で辻褄を合わせるのではなく**指定の時点で伝える**。

**既に上限を超えている定義は、切り詰めない。** はみ出したまま描き、画面で警告する。
勝手に値を書き換えると「なぜ列数が減ったのか」を後から追えなくなる。

### 検査（R11 で書き直し）

不変条件はこの2つ。**「一致」を無条件の約束として書いたことが、混在を検査から弾いた
原因だった。**

- **常に** — マス目は枠に収まる（`マス目の右端 ≤ 枠の右端`）
- **枝問が全員原稿用紙のときだけ** — 割り当て幅・描画幅・囲み枠の右端が一致する

混在（原稿用紙あり＋なし）では、枠は普通の枝問に合わせて広くなるのでマス目とは一致しない。
`__tests__/answer-sheet-builder/manuscriptWidth.test.ts` に、混在・`layoutWidth` 明示の
兄弟・親に `layoutWidth` 明示の3つを足した。

### 積み上げるのは実効幅の最大値（R11 指摘1）

**原稿用紙を持つ枝問だけの最大値を親の右端にすると、隣にいる普通の解答欄がマス目の幅まで
押し込まれる**（A4縦・既定設定で 160mm → 48mm、`layoutWidth: "1/2"` の兄弟は 75mm → 19mm、
横配置では親の小問に明示した `"1/2"` まで 90mm → 68mm に上書きされていた）。
原稿用紙を持たない枝問も「元の規則で決まる幅」を実効幅として言う。

```
親の必要幅 = max(各枝問の実効幅)
  実効幅 = 原稿用紙あり → 基準行高 × 倍率 × 列数 + 番号欄
           原稿用紙なし → 元の規則で決まる幅（layoutWidth の分数ぶん / 無ければ領域いっぱい）
```

「元の規則で決まる幅」は**幅を書き換える前**の領域幅から出す。書き換えたあとの
`layoutWidth` から出すと縮んだ幅を基準にしてしまうので、`buildSubGridLayout` が生の小問を
受けてその中で書き換えを閉じ、返すセルの `item` は生の小問のままにしてある。

### 列数の入力（R11 指摘2）

列数の入力欄に段幅由来の上限で丸める指定（`max` / `clampInt` の上限）を置かない。
A3 で 20 列として作った用紙を A4 へ切り替えると、数値入力の下矢印を1回押しただけで
ブラウザが先に `value` を `max` へ寄せ、`onChange` が上限の値で発火して元の値が消える。
入力で止めるのは桁あふれだけで、超過は警告で伝える。

## 段階44 — 採点領域を複数の矩形にし、途中改段組を入れる（後回し）

**OWNER 決定・2026-08-21。** 単独では着手しない。**複数領域の採点を機能として設計し、
途中改段組と合わせて実装する。**

### なぜ1つの段階なのか

途中改段組は原稿用紙を段またぎで割る。**割った瞬間に、1つの採点領域が紙の上で2つの矩形に
なる。** 採点・注釈・出力の全経路が「1領域＝1矩形」を前提にしているので、分割だけを先に
入れると採点が壊れる。だから片方だけでは入れられない。

### 複数領域の採点（検討事項・OWNER 提起）

**別欄に書かせた途中過程を、設問と一緒に採点したい。** 解答欄と、離れた場所にある
途中過程の欄が、**1つの設問の採点対象**になる。段またぎで割れた原稿用紙は、この一般形の
特殊な場合にすぎない。

決めること:

- **一覧表示と詳細表示** — 採点画面で、複数の矩形をどう見せるか。全部を並べて一度に見せるか
  （一覧）、1つずつ大きく見せるか（詳細）、その行き来をどうするか
- **矩形の順序** — 何番目の矩形か、を何で決めるか（**序数を key にしない**。同定は id）
- **アノテーションの帰属** — 注釈はどの矩形に属するか。矩形をまたぐ注釈を許すか
- **切り出し画像** — いまは1領域＝1画像。複数矩形をどう1枚にするか（並べる／別々に持つ）
- **出力** — Excel・PDF・個人成績表で、複数矩形の設問をどう出すか
- **OMR** — マーク欄が複数矩形になる場合があるか

### 途中改段組（設計は確定・実装は上記と同時）

**分割の単位は「行」。**

- **原稿用紙** — マス目の行がそのまま分割の単位。20行なら切れ目の候補が20個ある
- **それ以外の解答欄** — 高さが2でも3でも**まるごと1行**。切れ目は無い

いまの実装は原稿用紙を「高さ `rows × 倍率` の1行」に潰している
（`gridBuilder.ts:186-191`）。通常のセルと同じ形にしてしまっているので切れ目が消えている。
ここを**行の集まりとして持てるようにする**のが土台になる。

いまの配置ループ（`computeMultiPageLayout.ts:689`）は、

```ts
if (colCurrentY[...] + spacingHeight + majorHeight > contentMaxY &&
    colCurrentY[...] > contentTop) {
```

第2条件のため、**段の先頭に置いた大問が入りきらない場合はそのまま溢れる**。次の段へも
次のページへも送られない。これが「大問内分割が未実装」の実体である。

### 強制改段組と、分離禁止の3スイッチ

**加算だけで済ませる。** `NextPlacement`（`"inline" | "break"`）の union を延ばすと既存の
値の意味に手が入るので、**別の列**を足す。

分離禁止は **ASB ごと**（`AsbDefinition` の列）の3スイッチで、**どの深さの行を切れ目として
認めるか**を決める。

| スイッチ               | オンのとき                                              |
| ---------------------- | ------------------------------------------------------- |
| 大問の途中で分離しない | 小問の境目の行も使わない＝大問はまるごと1つの段へ       |
| 小問の途中で分離しない | 枝問の境目の行も使わない                                |
| 枝問の途中で分離しない | **原稿用紙の行を使わない**＝原稿用紙はまるごと1つの段へ |

**既定値は未決**。3つともオンで始めれば既存の解答用紙の見た目が変わらない、という利点が
ある（分割は着手時に改めて決める）。

### 将来の案（いま混ぜない）

**段組セクション** — 大問より上の単位で段組みを変える。「ここからは1段」「ここからは2段」
という区切りを置く。段組みの設定が用紙全体で1つしか無いという制約を解くもので、
**別の軸**なので段階44 には混ぜない（OWNER 提起・2026-08-21）。
