## 段階71 — 撮影の spec を書き直す

**リリースの成果物ではない。** 出力（`__tests__/screenshots/output/`）は `.gitignore`
済みで `src` からも参照されていない。使い方ガイドの図は画面の中の SVG とアニメで、
撮った画像は使っていない。だから急がないが、**部分的な手直しでは足りない。**

### 何が壊れているか

|                                                    |                                                                                                                                                                      |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `waitForTimeout` が48箇所                          | 条件ではなく秒数で待っている。遅いうえ、機械が重い日は途中の絵が撮れる                                                                                               |
| `catch` が29箇所                                   | **ログインの失敗すら `console.warn` だけ**。ログインできなければ30枚ともログイン画面が撮れて、それでも「成功」で終わる                                               |
| ポート3000 を `reuseExistingServer: true` で再利用 | **e2e の設定が「その罠がある」と明記して避けているもの**が、こちらには残っている。`npm run dev` を開いたまま撮ると**そちらのコードに対して**撮れ、`.next` も奪い合う |
| 900行に seed と撮影が同居                          | 状態をモジュール直下の `let` で持ち回り、章をまたいだ順序に暗黙に依存                                                                                                |
| 抜けている画面                                     | **8. 採点確定**（段階67）と**監査ログ**（段階69）。どちらもこの版で生まれた画面                                                                                      |

**ログインの握り潰しとポート3000 の再利用は、部分的な手直しでは直らない**（前者は
全体の失敗の扱い、後者は設定の作り）。だから書き直す。

### 画面サイズについて

既に `1440×900` で明示されており、効いている（出力の PNG で確認済み）。
**足りないのは2つ。**

- **なぜ 1440 なのかが書かれていない。** 一覧の操作は幅で「…」へ畳まれるので
  （段階64）、**この数字が図に写るものを決めている**。理由を残さないと、誰かが
  軽い気持ちで変えて図から操作が消える
- **1倍で撮っている。** 資料に貼ると粗い。`--force-device-scale-factor=2` で
  2倍にできる

## 段階72 — 開発時のデータ置き場をリポジトリの外へ

`electron-src/lib/dataManager.ts:36`

```js
} else {
  // 開発環境の場合
  const rootPath = process.cwd()   // ← リポジトリの根
}
// → getDataDirectory() = <リポジトリ>/data
```

**開発と運用が同じ置き場を見ている。** 0.17.0 の直前に、配布物へその中身が丸ごと
入っていたのが見つかった（[completed-work.md](./completed-work.md) の「塊D」）。
`forge.config.js` の除外を許可制へ裏返し、できあがりを見て止める関門も置いたので
いまは塞がっているが、**根はここ**である。

置き場を `~/Library/Application Support/…` などへ移せば、

- 配布物への混入が**構造的に**起こらなくなる（許可制の除外は二重の歯止めとして残る）
- `.gitignore` の `data/` も要らなくなる
- 文書に「開発時のデータ置き場はリポジトリ直下」と書かなくて済む

**移す手順が要る。** 既にそこで運用している人（＝自分）のデータを、新しい置き場へ
運ぶ道を用意しないと、次の起動で空のDBが生まれる。

## 段階44 — 採点領域を複数の矩形にし、途中改段組を入れる（後回し）

**OWNER 決定・2026-08-21。** 単独では着手しない。**複数領域の採点を機能として設計し、
途中改段組と合わせて実装する。**

### なぜ1つの段階なのか

途中改段組は原稿用紙を段またぎで割る。**割った瞬間に、1つの採点領域が紙の上で2つの矩形に
なる。** 採点・注釈・出力の全経路が「1領域＝1矩形」を前提にしているので、分割だけを先に
入れると採点が壊れる。だから片方だけでは入れられない。

### 複数領域の採点（検討事項・OWNER 提起）

**別欄に書かせた途中過程を、設問と一緒に採点したい。** 解答欄と、離れた場所にある
途中過程の欄が、**1つの設問の採点対象**になる。段またぎで割れた原稿用紙は、この一般形の
特殊な場合にすぎない。

決めること:

- **一覧表示と詳細表示** — 採点画面で、複数の矩形をどう見せるか。全部を並べて一度に見せるか
  （一覧）、1つずつ大きく見せるか（詳細）、その行き来をどうするか
- **矩形の順序** — 何番目の矩形か、を何で決めるか（**序数を key にしない**。同定は id）
- **アノテーションの帰属** — 注釈はどの矩形に属するか。矩形をまたぐ注釈を許すか
- **切り出し画像** — いまは1領域＝1画像。複数矩形をどう1枚にするか（並べる／別々に持つ）
- **出力** — Excel・PDF・個人成績表で、複数矩形の設問をどう出すか
- **OMR** — マーク欄が複数矩形になる場合があるか

### 途中改段組（設計は確定・実装は上記と同時）

**分割の単位は「行」。**

- **原稿用紙** — マス目の行がそのまま分割の単位。20行なら切れ目の候補が20個ある
- **それ以外の解答欄** — 高さが2でも3でも**まるごと1行**。切れ目は無い

いまの実装は原稿用紙を「高さ `rows × 倍率` の1行」に潰している
（`gridBuilder.ts:186-191`）。通常のセルと同じ形にしてしまっているので切れ目が消えている。
ここを**行の集まりとして持てるようにする**のが土台になる。

いまの配置ループ（`computeMultiPageLayout.ts:689`）は、

```ts
if (colCurrentY[...] + spacingHeight + majorHeight > contentMaxY &&
    colCurrentY[...] > contentTop) {
```

第2条件のため、**段の先頭に置いた大問が入りきらない場合はそのまま溢れる**。次の段へも
次のページへも送られない。これが「大問内分割が未実装」の実体である。

### 強制改段組と、分離禁止の3スイッチ

**加算だけで済ませる。** `NextPlacement`（`"inline" | "break"`）の union を延ばすと既存の
値の意味に手が入るので、**別の列**を足す。

分離禁止は **ASB ごと**（`AsbDefinition` の列）の3スイッチで、**どの深さの行を切れ目として
認めるか**を決める。

| スイッチ               | オンのとき                                              |
| ---------------------- | ------------------------------------------------------- |
| 大問の途中で分離しない | 小問の境目の行も使わない＝大問はまるごと1つの段へ       |
| 小問の途中で分離しない | 枝問の境目の行も使わない                                |
| 枝問の途中で分離しない | **原稿用紙の行を使わない**＝原稿用紙はまるごと1つの段へ |

**既定値は未決**。3つともオンで始めれば既存の解答用紙の見た目が変わらない、という利点が
ある（分割は着手時に改めて決める）。

### 将来の案（いま混ぜない）

**段組セクション** — 大問より上の単位で段組みを変える。「ここからは1段」「ここからは2段」
という区切りを置く。段組みの設定が用紙全体で1つしか無いという制約を解くもので、
**別の軸**なので段階44 には混ぜない（OWNER 提起・2026-08-21）。

## 段階59 — 評定を実体にし、基準に無い評価を見せる（リリース後）

**OWNER との設計討議・2026-08-22。** 調査中（材料が揃い次第ここへ足す）。

### 出発点 —— 順序が逆になっている

> 結局さ、**成績というのが、あくまで評価の後にある**、という前提ですよね。まず評価があって、
> **それを何点として解釈するのか**、という思想があるから、評価が任意入力で、後付けで
> 点数変換を行っている。ここにちゃんと向き合わないと解決しない。（OWNER）

いまのコードは「**境界が評定を定義する**」という前提で書かれている（`ConstraintRulesEditor` の
`collectLabels` が境界からラベルを集める）。だが実際の思想は逆で、**評定が先にあり、境界は
そこへ至る一つの手段にすぎない**。だから結果表の任意入力（`resolveOverrideDirection` の
`"custom"`）が居場所を失い、「その他」扱いになっている。

**評定という実体が無いまま、それを使う側だけが4つある。** FK が張れず、文字列照合になり、
名前が `label` に濁り、任意入力が宙に浮く —— **全部同じ根**である。

| 役割                     | いまの表                                              |
| ------------------------ | ----------------------------------------------------- |
| **評定そのもの（語彙）** | **どこにも無い**                                      |
| 導く手段                 | `GradeItemBoundary`                                   |
| 直接下す                 | `GradeOverride`（**基準に無い値も打てる**）           |
| 後付けの解釈（何点か）   | `GradeConstraintLabelValue`                           |
| 混在を禁じる             | `GradeConstraintExclusionLabel`                       |
| 資料の評語               | `CourseworkLetterScale`（**同じ概念か別かは調査中**） |

### 決まった仕様（OWNER）

1. **評価は Excel から自由に貼れる。** プルダウンで選ばせる形にはしない
2. **全角→半角は、貼り付けた瞬間に確認する** —— 「全角文字が検知されました。半角文字で
   よろしいですか？」。設定として持たない（置き場所も、アーカイブに載せるかも問わずに済む。
   利用者はそれが効く瞬間にだけ判断する）
3. **大小文字は区別する。** `A` と `a` は別の評定（いまは `letterKey` の `.toUpperCase()` が
   畳んでいる。**その1行を落とす**）
4. **基準が1つ以上定められているとき、基準に定められていない評価のマスを赤くする**
5. **弾かない。そのまま保存する**

**typo に気づく場所は「基準を決めるとき」であって、評価するときではない**（OWNER）。だから
評価の画面に typo 防止の UI を持ち込まず、**赤いマスで気づかせる**。

### 正規化についての方針転換

当初は「語彙を先に宣言し、正規化で吸収して照合し、合わなければ拒否」と考えたが、**OWNER が
これを退けた**。正規化は「そう打ちたかったのだろう」という**推測**であり、このリポジトリが
他所で徹底している「黙って変換しない」に反する。

ただし**全角→半角は推測ではない**（表記の違い）ので残し、**スイッチで切れるようにする**。
**大小文字を畳むのは推測**なのでやめる。

**`normalizeInput` は撤去しない。** 撤去するのは `letterKey` の `.toUpperCase()` だけ。

### 資料側は既にこの形に近い

`CourseworkScoresContainer.tsx:46-64` に doc コメントごと在る。

> Excel から貼り付けた `１０` や `ａ` は間違いではなく表記の違いなので、弾かずに受け入れる。
> 文字評価の照合では**変換表のラベル側にも同じ正規化を通すこと**

**成績側だけがこの形になっていない**（境界から語彙を導き、上書きは素通し、正規化も照合も無い）。

### 決着（2026-08-22）—— 外部資料の側は実装済み `e2adfef9`

**話が2つ混ざっていた。** 貼り付けと自由入力の議論は**外部資料（Coursework）**の点数入力で、
成績（Grade）の評定とは別である。

**外部資料** —— 仕様どおり実装した。`A`/`a` を区別、全角は貼り付け1回につき一度だけ尋ねる
（設定は持たない）、変換表に無い評語も保存する、赤は変換表が1本以上あるときだけ、評価項目の
画面に件数つきで列挙する（変換表へ足す導線は置かない）。**計算で欠測になるのは仕様**なので
手当てしない。

**成績の上書きも自由でなければならない**（OWNER）。自動算出できない「**／**」を、校長判断で
評定として与えることがある。「基準のない自動算出成績は不要」は**自動算出の側**の話で、
上書きの側は逆である。外部資料と同じ形（そのまま保存・赤・列挙）にするのが筋。

**観点間制約は、基準外の評定を自動的に外してよい**（OWNER）。

> そもそも制約は**自動算出において**チェックするもの。校長判断については観点だけでなく評定も
> 一括して判断するもの。**できる範囲で検査すればよい。**

つまり**いまの挙動がそのまま仕様**である —— 基準外の観点は平均の母数から落ち、比較先が
基準外なら違反なしになる。**「黙って母数が縮む」を問題として扱わない。** 手を入れない。

**`GradeFrozenScore` の名前** —— 採点側が「確定」を `07-2-finalize` と呼ぶ計画なので、
`Finalize` 系へ揃えるかは別途。

### 実装で決めること（未定）

- **全角→半角スイッチの置き場所** —— 成績・資料ごと（アーカイブに載る）／アプリ全体の設定
  （載らない）／評価項目ごと。**アーカイブと一緒に持ち運ばれるかで意味が変わる**
- 語彙テーブルを作るなら、**一致しない生の値をどう保つか**。`overrideLabel`（生）＋
  `gradeLabelId`（解決済み・null 可）の2列が素直
- 赤くするのは基準の画面だけか、**評価を入れる画面でも**か
- **赤い評価がその先（換算・分布・出力・確定・アーカイブ）でどう扱われているか** —— 調査中。
  ここが次の設計の入口
- `CourseworkLetterScale` を同じ語彙へ寄せるか（**同じに見えて違う可能性**。資料は評語ごとに
  点数を持ち、成績の換算は制約ごとに数値を持つ）

### リリースには含めない

語彙の実体化・migration・4画面・アーカイブの版上げと変換器に波及し、**「基準に無い評定を
どう足すか」という UI 設計**も新たに要る。

**段階33 で決めた `@unique` の判断は、この設計が入れば作り直しになる**（`(constraintId, label)`
が `(constraintId, gradeLabelId)` ＝ uuid のみの複合 unique へ移る）。ただし**入るまでは今の
判断が正しい**ので無駄にはならない。

## 段階60 — アーカイブ4種を1つに統合する（**将来・リリース後**）

**OWNER 予定・2026-08-22。** いまアーカイブは**4種類**ある。

| 種                              | 現行版 | 変換器 |
| ------------------------------- | ------ | ------ |
| `.examarchive`（試験）          | 1.26.0 | 25本   |
| `.coursework`（試験外成績資料） | 1.1.0  | 1本    |
| `.grade`（成績）                | 1.15.0 | 8本    |
| `.asb`（解答用紙）              | 1.4.0  | 4本    |
| `.student`（生徒）              | 1.0.0  | 0本    |

**（数えると5種。4種というのは `.student` を除いた数か、統合の対象が4つという意味かを確かめること。）**

### なぜ統合するのか（推測ではなく、いま観測できている食い違い）

**同じことを4回別々に書いている。** 2026-08-22 に全種を実測して分かったことを、統合の材料として残す。

- **取り込みの解釈が種ごとに違う** —— 試験は**id が一致したら自動でマージ**（選べない）、資料は**人が統合先を指定**、成績は**名前で lookup し作らない**（`allowCreate: false`、これは仕様）
- **同じ生徒・学級を、種ごとに別のコードで照合している** —— `merge/matchers/`（試験）と `coursework-archive/idRemapper.ts`（資料）と `gradeArchiveImporter.ts`（成績）。段階33 で `new Map(rows.map(...))` が黙って最後の1件を採る穴を**2箇所で同時に直した**のは、この重複が原因
- **既定値の埋め方も種ごと** —— 試験は `archiveExtractor` の1か所へ寄せた（段階58）が、`gradeArchiveImporter` には**同じ形の `for...of` が14か所**残っている
- **版の検出も揃っていない** —— 試験は manifest ＋ 形状フロア、成績は**形状のみ**（`manifest.version` が 1.6.0 固定で嘘をついていた歴史がある）
- **`createdAt` / `updatedAt` が5種すべてで取り込み時刻へ倒れる**（アーカイブは値を持っているのに使わない）

### 統合するとき、まとめて解けるもの

- **人が統合先を選ぶ導線**（段階61 で試験へ入れる）を1つにする
- **生徒・学級・タグの照合**を1つにする（`humanKeyMatching.ts` が既にその第一歩）
- **既定値の埋め方**を1つにする（**変換チェーンの「あと」で埋める**という段階58 の知見を全種へ）
- **`createdAt` / `updatedAt` の扱い**を1つ決める（判断待ち）
- **`.grade` に利用者のセクションを足す**（OWNER 裁定・2026-08-23 に**ここへ畳んだ**）。
  `GradeFrozenScore.frozenByUserId` を行のまま書き出すのに成績アーカイブは利用者を
  持たないので、取り込み側は同じ id の利用者が偶然居なければ **null（操作者不明）へ倒す**。
  試験側と違って別人へすり替わりはしないが、**「誰が確定したか」は端末をまたぐと必ず
  消える**。試験アーカイブは 2026-08-23 に「参照される利用者を全員入れる」へ直した
  （`e4f7bf0c`）ので、**統合するときはその形へ寄せる**

### やらないと決めていること

- **`.grade` の名前ベース外部参照は仕様**（試験・小計・領域はアーカイブに含めず lookup のみ）。統合しても、この非対称は残す
- **資料の評語（`CourseworkLetterScale`）と成績の評定は別概念**（前者は配点表で、同じ `S` が項目ごとに 6/12/18/30 点）。同じ語彙へ寄せない

### 先に片付けておくべきこと

**統合の前に、種ごとの往復が全部緑であること。** 2026-08-22 時点で `.coursework` / `.grade` / `.asb` / `.students` は新規取り込みで損失ゼロ、`.examarchive` は段階58 で4件を直した。**この状態を回帰テストで固定してから統合に入る**（`__tests__/import-export/scenarios/roundTripFieldFidelity.test.ts` が試験のぶん）。

## 将来の検討 — 畳みを取り消せるようにする（**いまは実装しない**・OWNER 判断 2026-08-22）

`_id_merge` は「**何が何になったか**」しか持たない。だから通知を見ても**元に戻せない**。

**畳む前の姿**（消える敗者の行の全列と、付け替える子の付け替え前の姿）を残せば戻せる。
SQLite の Session 拡張には `sqlite3changeset_invert()` があり、changeset を反転して適用
できる（**`better-sqlite3` から使えるかは未確認**）。使えないなら自前で JSON に残す。

**分散ならではの落とし穴**: 戻しても**次の同期でまた畳まれる**。相手には `mergedInto` の
墓標が残っているため。だから操作は「取り消し」ではなく **「2つに戻して、片方の名前を変える」**
になる。名前を変えれば unique がぶつからない。**利用者がやりたいことでもある。**

**期限は切ってよい。** ただし `_changelog` の理屈（7日で捨てる。捨ててもフルマージで
正しくなる）は**ここには使えない**。

|                                 | 期限           | 捨てたらどうなるか               |
| ------------------------------- | -------------- | -------------------------------- |
| `_changelog`                    | **7日**        | フルマージで正しくなる           |
| `_id_merge`（何が何になったか） | **無し**       | 子の付け替えに要る。捨てられない |
| **元の姿**（戻すため）          | **切ってよい** | **戻せなくなるだけ**             |

**畳みが頻繁に起きるなら、それ自体が設計の失敗**（unique を置くべきでない表に置いている）
なので、記録が膨らむこと自体が警告になる。
