## 小計グループの差分化 — 更新を差分書き込みへ直す

**いま実際にデータが消えている。** 見つかったのは 2026-08-20、規約に沿って計画を見直す
過程で。

### 症状

**小計点グループの名前を1文字直して保存すると、04 で設定した設問の割り当てが全部消える。**
その小計を参照している成績のデータソースも消える。割り当て直しても、`Subtotal` の id が
変わっているので元には戻らない。

### 機構

`electron-src/lib/prisma/subtotalGroup.ts:97`

```ts
await tx.subtotal.deleteMany({ where: { subtotalGroupId: id } }) // ← 全部消す
return await tx.subtotalGroup.update({
  data: { name: data.name, subtotals: { create: data.subtotals } }, // ← 作り直す
})
```

`Subtotal` には**カスケードする子が2つ**ある。

```prisma
model Subtotal {
  cropSubtotals    CropSubtotal[]      // onDelete: Cascade
  gradeDataSources GradeDataSource[]   // onDelete: Cascade
}
```

同期にも毎回 tombstone と新しい id が流れる。

### 棚卸し（2026-08-20）

`electron-src/lib/` の全書き込みから「`deleteMany` と `create` が同居するもの」を機械で
拾うと **18件**。うち**消される行に孫がいるのは `updateSubtotalGroup` だけ**だった
（他は葉＝タグの紐付け・選択肢・境界・刻みなど）。

**同じ形は既に潰されている。** `updateCourseworkItem` のコメントが証拠になっている。

> かつてここが刻みの配列を受け取り `deleteMany` → `create` していたため、項目名を1文字
> 直すだけで全行の id が振り直されていた。

段階11（04 の割り当て）・段階17（タグの紐付け）でも同じ形を潰した。**小計グループだけが
残っていた。**

### 直し方

`setAsbDefinitionTags` と同じ形にする。**外れたものだけ消し、変わったものだけ更新し、
増えたものだけ作る。**

- **突き合わせは id で。** `Subtotal` は `@@unique([subtotalGroupId, name])` を持つが、
  名前で突き合わせると「並べ替えと改名が同時に来たとき」に別物として扱ってしまう。
  画面側の `SubtotalFormData` は既に `id` を持っている
- 触った行が無ければ何も書かない

### 検査

- **グループ名を変えても、設問の割り当て（`CropSubtotal`）が残る**
- 小計項目を1つ消しても、残った項目の id が変わらない
- 小計項目を並べ替えても、id が変わらない

ガードは外すと実際に落ちることを確認してから採用する。

## 削除前の数え直し — 全ての削除へ広げる（OWNER 決定・2026-08-20）

削除の確認は「消すと何を巻き添えにするか」を数えて見せる。**数え終わってから利用者が押す
までの間に、他の教員が書き足す窓**が残っている。

**「消す前に数え直して、増えていたら中止する」を共通の作法にする**（OWNER 決定）。答案の
削除だけに入れると一貫しないため。

### いまどうなっているか

答案の削除は**すでにトランザクションの中で数え直している**
（`deleteStudentAnswer` → `countStudentAnswerScoreData`）。ただし返り値（表示用）に使うだけで、
**中止の判断には使っていない**。繋げば塞がる。

### やること

1. 削除の確認を持つ経路を数える（答案・学級・生徒・試験・資料）
2. **共通の形を1つ決める** — 「利用者に見せた件数」を削除の要求に添え、main が消す直前に
   数え直し、食い違えば中止して差分を返す
3. 画面は「他の教員が採点しました。もう一度確認してください」と伝えて数え直す

### 注意

- **数える定義を、見せたものと揃える。** `deleteStudentAnswer` のコメントが指摘している
  とおり、削除自体は `unscored` の初期化行も含めて全て消すので**行数とは一致しない**。
  比べるのは「利用者から見た採点実績」でなければならない
- 窓は縮むが消えない（数え直しと削除は同じトランザクションに入れる）

## 作成＋タグ付け — 判断は「小計グループの差分化」の後で

新規作成のあとタグを紐付ける流れが2つある（小計グループ・試験）。いまは**作った相手を覚えて
再試行では更新へ回す**ようにしてあり、二重作成は起きない（2026-08-20）。

本筋は「**途中まで成功した状態そのものを作れなくする**」ことで、それには作成とタグ付けを
1つの口にまとめて main のトランザクションで包む。

**ただし先に「小計グループの差分化」を済ませる。** いまの `updateSubtotalGroup` は
「木をまるごと置き換える」書き込みで、そこにタグを足すと**規約から外れた経路を太らせる**
だけになる。段階15〜17 は木ごと書く経路を4つ（新規作成・undo/redo・複製・アーカイブ取り込み）
に絞っており、**新規作成は許される側だが更新は違う**。

差分書き込みへ直したうえで、まとめるかを判断する。やる場合の条件:

- payload 型は必ず `Parameters<typeof window.electronAPI.x>[0]` と Prisma 型から導く
  （手書きが検出を殺した実例が指摘 #3 にある）

## 段階20 — 競合で負けた行の子を、ライブラリ側で引き取る

**作業先はこのリポジトリではない**（`~/dev/sqlite-nas-sync`）。それでもここへ置くのは、
協調採点が成り立つ前提そのものだからで、宙に浮かせると誰も拾わない。

### 何が起きているか

2端末が同じものを独立に作ると、中身は同じで id だけ違う行が2つできる。ライブラリは
これを LWW で1行へ畳む（`conflict.ts:207`）。**畳み方が「負けた行を消す」なので、負けた
行に子がぶら下がっていると巻き添えになる。**

帰結は2つあり、どちらも**画面に何も出ない**。

1. **負けた側の子データが消える。** 2人の教員が同じ生徒を同じ試験へ加えて採点すると、
   **片方の採点がどこにも残らない**（負けた `ExamStudent` の削除が `QuestionScore` へ
   カスケードする）
2. **同期がその相手から永久に止まる。** 勝った端末は相手の子を置く場所が無く外部キー
   違反を出す。適用ループは相手1人ぶんが1トランザクションで、読んだ位置も巻き戻るので、
   次回も同じ所で落ちる。**無関係なテーブルの変更も以後いっさい届かない**

**実測済み**（3回試して `clientsSynced=0`、無関係な行も届かず）。詳細・再現手順・該当10
モデルは [sync-secondary-unique-hazard.md](./sync-secondary-unique-hazard.md)。

### 直し方

**負けた行を消す前に、負けた行を指している子を勝った行へ付け替える。**

付け替え先はライブラリが自力で辿れる。SQLite が `PRAGMA foreign_key_list` で「どの表が
この表を指しているか」を答えるので、**スキーマを知らなくてよい**。

これで上の2つが同時に片付く。詰まらなくなるのはその結果であって、目的ではない。

### 境界（できないこと）

- **負けた行の属性はマージできない。** 列の意味を知らないため、勝った行が総取りする。
  既知の穴として据え置く（`ExamSubtotalGroup` の2つのフラグが実例）
- **付け替えた子が子自身の制約にぶつかる場合**の扱いは未決。同じ LWW をもう一段回すのか、
  別に扱うのか
- **孫は動かさない**（子を指したままでよい）。要確認

### アプリ側で避ける案は採らない

「1:1 の表は id を親から決めれば衝突自体が起きない」は**実測で効くと確認したが採らない**
（OWNER 判断・2026-08-19）。id を内容から導出する形は 2026-08-03 の PR #1150 で3系統
（合成id・親の id 流用・uuidv5）すべて撤去され、`uuidIdCoverage.test.ts` が禁じている。
**方針には独立した根拠がある** — id が同一性を持つと、消して作り直した行が tombstone に
潰されて復活しない、という逆向きの事故が起きる（`20260803110000_unify_ids_to_uuidv4` の
冒頭に記載）。今回の実測はその根拠を崩していない。

### この修正が可能にすること

**FK を張れなかった列に張れるようになる。** 「親がまだ届いていない子を保留して再試行する」
が入れば、読む順による FK 違反が解ける。対象は `ScoreDecision.sourceQuestionScoreId` と
`ReturnSnapshot.capturedByUserId` の2件 → **段階22**。

### 併せて直すもの

**「LWW が畳む」と書いてある説明文に、「敗者に子がいない場合に限る」を足す。**
`uuidIdCoverage.test.ts` の冒頭と `schema.prisma` の3箇所（`:210` / `:283` / `:895`）。
いまの文面は次に読む人へ「ライブラリが全部畳んでくれる」と誤って伝え続ける。
**これは実装より先に済ませる。**

### 着手時期

段階19 までとは独立で、いつでも入れる。**ただし協調採点の実運用より前に入れること。**

## 段階21 — 採点行は、注釈を書くときに main が用意する

R7/R8 の指摘 #2 の2段目。**表示しただけで DB に行を作るのをやめる。**

### なぜ

`unscored` の行は情報を1ビットも持たない。**行の不在が既に全経路で未採点として読まれて
いる**からで、確定リゾルバ・成績算出（試験合計／設問単体）・Excel・個人成績表・平均行・
SP分析のどれも、行の有無と `unscored` を区別しない（全数調査は
[branch-review-findings.md](./branch-review-findings.md) #2）。

にもかかわらず作っている理由は1つだけ — **`DrawingAnnotation.questionScoreId` が必須のFK**で、
renderer が描く前に `questionScoreId` を必要とすること。**置き場所が要るという都合が、
「表示したら書き込む」という振る舞いになっている。**

副作用として、設問をめくるだけで空行が量産される（40人×30問で1教員あたり1200行）。行が
増えるほど[段階20 の衝突](./sync-secondary-unique-hazard.md)の機会も増える。

### 形

```
いま:     画面が先に行を作る → その id を持って描く → 注釈を保存する
これから: 画面は描く → 保存で「答案＋設問＋採点者」を送る
          → main が必要なら行を用意して、注釈をぶら下げる
```

**IPC は意図を運ぶ**（「この答案のこの設問に、この注釈を描いた」）。置き場所の都合は main
の内側へ入る。

- 注釈の保存・取得の口から `questionScoreId` を外し、`examStudentId` / `cropRegionId` /
  `userId` を受ける
- renderer のキャンバス層が `questionScoreId` を前提に組まれているので、そこを解く
- `status:"unscored"` を書いてよいのは、利用者が明示的に「未採点に戻す」を選んだときだけ

### 前提

**#2 の1段目（`setQuestionScore` / `ensureQuestionScore` への分割）を先に入れる。** あちらは
数行で採点消失を止める。この段階はそのあと、空行を作らない形へ進める。

### 併せて片付くもの

- `initializeScoringRecords`（`prisma/scoringInitializer.ts`）は呼び出し元ゼロで死んでいる。
  撤去する
- **リゾルバの `unscored` 除外は残す。** 注釈だけ付けて採点はまだ、という状態を表すのに
  `unscored` の行は今後も要る。除外はその不変条件の表明であって、掃き残しへの応急処置では
  ない。ただしコメントの理由を書き換え、型で守る（指摘 #16）

### やらないこと

- **旧版が量産した空行の掃海。** やる価値はあるが破壊的操作なので別途・要許可。条件は
  「`unscored` かつ 注釈が無く かつ `ScoreDecision.sourceQuestionScoreId` から参照されて
  いない」（後者は FK ではない生の文字列なので、消すとぶら下がりが残る）
- **アーカイブ側での間引き。** 「アーカイブは正本・存在について忠実復元」の裁定に反する

## 段階22 — FK の無い行参照に FK を張る

**OWNER 決定・2026-08-19。** `*Id` を名乗りながら `@relation` を持たない列が6件ある。うち
**実際に行を指している2件へ FK を張る**。

| 列                                    | 判断                           | `onDelete` |
| ------------------------------------- | ------------------------------ | ---------- |
| `ScoreDecision.sourceQuestionScoreId` | **列ごと削除**（下記）         | —          |
| `ReturnSnapshot.capturedByUserId`     | **張る**                       | `Cascade`  |
| `AuditLog.userId`                     | 張らない（削除後もログを残す） | —          |
| `AuditLog.scopeId` / `entityId`       | 張らない（多態。張れない）     | —          |
| `UserSidePanelSection.sectionId`      | 張らない（行を指していない）   | —          |

`capturedByUserId` は **`Cascade`**（OWNER 決定・2026-08-19）。利用者を消したら、その人が
記録した返却版も消える。

### `ScoreDecision.sourceQuestionScoreId` は列ごと消す（OWNER 決定・2026-08-19）

FK の張り方を論じる前に、**そもそもこの列が要らない**。

> 誰の採点結果を採用しているのかは**不明**である。2人が同じ「正答」を付けていたら、
> どちらを採用したのか、両方なのか、決まらない。**保存すべきは採点結果であって、
> 由来ではない。**

### なぜ今まで張れなかったか

**参照する側と参照される側が、別の端末で生まれるから。**

```
先生B の端末:  採点する        → QuestionScore が生まれる
OWNER の端末: B の判定を採用  → ScoreDecision が生まれ、B の行の id を指す
```

同期は**相手ごとに変更履歴を読む**ので、届く順に保証がない。OWNER を先に読むと、確定が
届いた時点で参照先の採点行がまだ無い。FK があればそこで `FOREIGN KEY constraint failed` に
なり、[段階20 の詰まり](./sync-secondary-unique-hazard.md)を**読む順だけで**引き起こす。

### だから段階20 が前提

段階20 の修正には「**親がまだ届いていない子を脇へ退避し、同じ取り込みの最後にもう一度
試す**」が含まれる。順序違いはこれで解ける。**段階20 より先にこの段階へ入ってはならない。**

### migration の手順

1. **ぶら下がりを掃除する** — 参照先が存在しない `sourceQuestionScoreId` /
   `capturedByUserId` を `NULL` にする
2. テーブルを作り直して FK を張る

**順番が逆だと不整合が残る。** `migrationDeployer` は `PRAGMA foreign_keys` 既定 OFF で走る
ので、**既存行は検証されない**。掃除せずに張ると、FK があるのに違反した行が残った状態に
なり、次に FK が効く経路（同期の適用）で初めて牙を剥く。

検証は空DB への `foreign_key_check` では足りない。**データを入れた写しへ適用し、
`foreign_key_check` と `sqlite_master` の定義文を目視する**（テーブル作り直しの FK 罠は
`project_migration_rename_fk_gotcha`）。

### 併せてやること

- **張らない4件に理由を1行書く。** `AuditLog.userId` だけは既に書いてある（手本）。
  多態の2列と `sectionId` は書かれていない。**意図か漏れかが読んで分からない状態を残さない**
- `UserSidePanelSection.sectionId` は行を指していないのに `*Id` を名乗っている。命名の
  見直し候補（別件）
