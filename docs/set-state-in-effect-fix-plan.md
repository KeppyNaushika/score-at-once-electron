# effect 内 setState の解消で入った回帰と、その修正計画

## 背景

`react-hooks/set-state-in-effect` の警告 63 件のうち、**effect の中で同期的に setState していた 20 件（B群）** を派生値化で解消した。手口と分類は [coding-style.md「effect の中で setState しない」](./coding-style.md#effect-の中で-setstate-しないreact-hooksset-state-in-effect) に、残った警告の扱いは `eslint.config.mjs` の該当ルールのコメントにある。

その差分に対する多角レビュー（26 エージェント / high）で 10 件が挙がった。**うち 4 件はこの差分で入った回帰**で、いずれも「effect が暗黙にやっていたリセット・再取得を、派生値化の際に落とした」という同じ原因を持つ。2 件は元からある不具合、4 件は挙動差・堅牢化。

この文書は、**どの画面のどの操作が、いま何をして、修正後に何をするようになるか**を1件ずつ記録し、修正方針を確定させるためのもの。各項目は次の順で書く。

1. **画面・機能** ── どこを開いて何をする話か
2. **再現手順** ── 手で確かめる手順
3. **いま起きること**
4. **修正後に起きること**
5. **手当て** ── 実際に書き換える箇所

## A. この差分で入った回帰

### A-1. 裁定パネルで、見ていたマスが別のマスに入れ替わる

#### 画面・機能

`/exams/[examId]/07-score-at-once`（採点実行）の「採点の割り当てと確定」パネル。

このパネルが扱う **「セル」とは、受験生徒 × 設問の1マス**（型は `ScoreDecisionCell`）。つまり「田中太郎さんの 大問2(1)」という1つの採点対象を指す。全マスが並ぶのではなく、**裁定が必要になったマスだけ**が並ぶ。裁定が必要になる理由は2つある。

| 理由       | 意味                                                           | 出力への影響               |
| ---------- | -------------------------------------------------------------- | -------------------------- |
| `conflict` | 複数の採点者が違う点を提案していて、有効スコアが決まらない     | そのマスは未採点として出る |
| `stale`    | 一度確定したが、その後に新しい提案が入った（確認し直しが必要） | 確定値が出る               |

画面構成は左右2ペイン。

- **左**: 設問ごとの行（担当者・進捗）と、その下に裁定対象のマス（生徒名つき）
- **右**: 左で選んだ**1マス**について、採点者ごとの提案を並べて比較し、「この点数で確定」を押す

#### `selected` とは何が選ばれているのか

コード上の `selected` は **教員が左ペインでクリックした「どの生徒の、どの設問のマスか」** を保持する状態で、中身は生徒と設問の id 2つだけ。

```ts
/** 選択中セルの所在（設問とセルは必ずペアで持つ — 添字では引かない） */
interface SelectedCell {
  cropRegionId: string // どの設問か
  examStudentId: string // どの受験生徒か
}
```

これと別に `selectedEntry`（**実際に右ペインへ表示しているマス**）がある。両者を分けているのは、選んだマスが裁定を終えて一覧から消えることがあるため。消えたときは先頭のマスへ寄せて表示する。

- `selected` = **教員が選んだマス**（意思）
- `selectedEntry` = **いま表示しているマス**（結果）

#### 再現手順

1. 教員 P と教員 Q が同じ試験を開き、P が「採点の割り当てと確定」を開く
2. 一覧に裁定対象がマス X・マス Y … と並んでいる。P が X を選んで「この点数で確定」を押す
3. X は裁定済みになり一覧から消える。右ペインは自動で先頭のマス Y に切り替わる
4. P は Y の提案を読み、「この点数で確定」を押そうとする
5. その間に Q が X の点数を変更する（または X が `stale` として再び裁定対象になる）
6. パネルが更新される

#### いま起きること

手順 3 で表示は Y に変わるが、**`selected` は X を指したまま**になっている。手順 6 で X が一覧へ戻ると `selected` が再び X にヒットし、**右ペインが Y から X へ勝手に切り替わる**。P が Y のつもりで押した「確定」が、**X の生徒・設問へ確定点として書かれる**。

削除前の effect は、手順 3 で先頭へ寄せた結果を `selected` へ書き戻していた（＝ X の選択を捨てていた）ので、この入れ替わりは起きなかった。

#### 対応: 放置（既存 issue と抱合せ）

**この差分では直さない**（所有者判断）。裁定パネルは UI として作り直しが必要で、選択の保持だけを直しても土台が変わる。既存 issue と抱合せで扱う。

作り直しの際に解消すべき指摘（2026-08-10 に所有者から）:

| #   | 指摘                                           | 現状                                                                                    |
| --- | ---------------------------------------------- | --------------------------------------------------------------------------------------- |
| 1   | 生徒解答画像が無い                             | 氏名・設問名・提案の文字だけ。答案を見ずに裁定させている                                |
| 2   | 左の設問一覧が既存UIと違って見にくい           | `QuestionAssignmentRow` が独自実装。`ScoringSidePanel/QuestionNavigator` を使っていない |
| 3   | 「採用」ボタンだけに当たり判定があるのが不可解 | 行は `<div>`、ボタンだけが `onClick` を持つ                                             |
| 4   | 採点者名をもっと大きく                         | `text-xs text-gray-500` で更新時刻と同列                                                |
| 5   | 確定する判定に一致する採点者は全員強調すべき   | 強調が「採用した1件」だけ（`sourceQuestionScoreId` 一致）で、判定一致を見ていない       |
| 6   | 食い違いの説明メッセージを毎回出す必要はない   | `reason === "conflict"` なら常時バナー表示。裁定対象はほぼ全部 conflict                 |

5 を「確定する判定と一致する提案を全て強調」に変えると 3 も解ける（行クリック＝その判定を選ぶ、となり「採用」という別概念が要らなくなる）。その場合、確定行に残す採用元（`sourceQuestionScoreId`）をどう決めるかが仕様上の論点になる。

なお、この画面の選択保持を直す場合でも eslint の警告は出ない（イベントハンドラで済むため）ので、**C群には入らない**。

### A-2. 表に入れた無効な値が、警告も出さずに消える

#### 画面・機能

スプレッドシートのように直接入力できる共通の表（`EditableTable`）を使う3画面。

| 画面                                   | 用途                         | 無効値の警告 |
| -------------------------------------- | ---------------------------- | ------------ |
| `/coursework/[courseworkId]/04-scores` | 試験外成績資料の点数入力     | **あり**     |
| `/students`                            | 生徒の一括登録モーダル       | なし         |
| `/classrooms/[classroomId]`            | 学級への生徒一括登録モーダル | なし         |

この表は、セルに文字を打ち、**フォーカスを外した時点（blur）で入力値を親へ渡す**（以下この操作を「入力の反映」と呼ぶ。A-1 の「点数の確定」とは別物）。列に「有効な値かどうか」の判定（`meta.validate`）が付いている場合、無効な値は次の2つで警告される。判定が付いているのは 04-scores の**点数列と加減点列**だけなので、実害があるのはこの画面。

| 警告                                | 見え方                                               |
| ----------------------------------- | ---------------------------------------------------- |
| 赤背景（`bg-red-100 text-red-700`） | 値が無効な間ずっと出る（正しい値に打ち直すと消える） |
| `<input>` の `title` 属性           | **マウスを載せている間だけ**ブラウザが出す           |

`title` は常時表示される要素ではないので、出しっぱなしになるのは赤背景だけ。

#### 再現手順

1. `/coursework/[courseworkId]/04-scores` を開く（A/B/C の文字評価の評価項目がある状態）
2. ある生徒の評価セルに、変換表に無い記号（例 `S`）を入力する
3. Tab キーでセルを離れる

#### いま起きること

入力欄は**元の値に戻り、赤背景も出ない**（マウスを載せても警告文は出ない）。

`S` は変換表に無いので、受け取った側（`CourseworkScoresContainer`）の「未定義の評価記号は無視」分岐が何も保存しない。表を完全な制御コンポーネントにしたことで、表示は常に親の持つ値になったため、**弾かれた値は画面から消える**。教員は入力できたと思い込む。数値でない文字列を数値列に入れた場合も同じ。

改修前は表がローカルに写しを持っていたので、`S` が赤いまま残り「保存されません」と伝わっていた。

> 満点超過（`/100` の列に `150`）も現状は同じく弾かれるが、**外部成績で満点超過を許容するかは仕様の論点**として別に扱う（[満点超過の扱い](#満点超過の扱い外部成績)）。ここでは仕様に依存しない例で説明する。

#### 修正後に起きること

`S` は赤背景のまま欄に残る（マウスを載せれば `title` の警告文も出る）。正しい値に打ち直せば通常どおり保存され、赤も消える。

#### 手当て

セルが持つ下書き（打ちかけの文字列）を、**それを打ち始めたときの確定値と対で持つ**。この差分の他の箇所で使っている「結果に入力を同梱して引き直す」形をそのまま当てる。

```ts
// 下書きは「どの確定値に対して打ったものか」を一緒に持つ。値が入れ替われば
// 一致しなくなって自然に外れるので、blur で消す必要がない
const [draft, setDraft] = useState<{
  committedValue: string
  text: string
} | null>(null)
const committedValue = String(getValue() ?? "")
const strValue =
  draft?.committedValue === committedValue ? draft.text : committedValue

const onBlur = () => {
  table.options.meta?.updateData?.(row.index, column.id, strValue)
  // 下書きは消さない。親が受け付ければ確定値が変わって勝手に外れ、
  // 弾かれれば残って赤いまま見える
}
```

これで3つの経路が同時に揃う。

| 打った値                         | 親の反応       | 画面                                     |
| -------------------------------- | -------------- | ---------------------------------------- |
| 有効な値                         | 保存する       | 確定値が変わり下書きが外れる（通常表示） |
| 無効な値（満点超過・未定義記号） | 何もしない     | 下書きが残り**赤いまま**                 |
| 無効な値を残したまま他端末が同期 | 確定値が変わる | 下書きが外れ、同期後の値が見える         |

3行目が重要で、**単に「blur で下書きを消さない」だけにすると他端末の変更を覆い隠す**。改修前は表側の写しが差し替わることでこれを免れていたので、同じ性質を対で持つことで保つ。

#### 併せて直す: 弾いたことが伝わっていない

弾かれたことを伝える手段が `<input>` の `title` 属性しかない。この表は Tab / Enter でセルを移動する**キーボード前提**の設計なので、ホバーしない限り警告文に到達できない。赤背景は常時見えるが、**満点超過なのか未定義の記号なのか数値でないのかを区別できない**。CLAUDE.md の「エラーは非中断的に通知（トースト等）」からも外れている。

**弾くのであれば伝える義務がある**（所有者判断）。手段はトーストと赤背景の2つに絞る。

```
「S」は保存されません（入力できる値: A / B / C / F）
```

期待値の文言は列が既に `meta.placeholder` として持っている（文字評価なら記号の一覧、数値なら範囲）ので、それを流用し列ごとの新しい設定は増やさない。

#### 貼り付けは別経路であることに注意

`handlePaste` は `EditableCell` を経由せず、貼り付けた塊から `newData` を組んで直接 `onDataChange` を呼ぶ。**セルの下書きを通らないので、貼り付けで弾かれた値は赤くならない。**

改修前も実質同じだった。貼り付け直後は表側の写しに不正値が残って赤くなるが、**同じ貼り付けの中の1マスでも受理されると**親のデータが差し替わり、写しごと上書きされて赤も消える。40人分を貼って3マスだけ不正、という状況ではその3マスは赤くもならずに消えていた。

| 経路            | 赤背景 | トースト           |
| --------------- | ------ | ------------------ |
| 1マスずつの入力 | 出る   | 出る（理由つき）   |
| 貼り付け        | 出ない | 出る（件数へ集約） |

```
45件の値が保存されませんでした（貼り付ける位置がずれていませんか？）
```

貼り付けたセルまで赤くするには、表が「貼り付けたのに保存されなかった入力」を持つ必要があり、行の同定に実体キー（`getRowId` の追加と呼び出し元3画面の更新）が要る。**位置ずれは「0件か、ほぼ全件か」に寄る**ため件数で足りると判断し、常設の移動導線（`‹ 前へ 次へ ›`）とともに見送る。必要になったら足す。

#### 弾く前に受け入れる: 表記ゆれの正規化

素点列を全許容にした後、弾かれ得るものは2種類しか残らない。

| 種類                           | 例                                           | 扱い           |
| ------------------------------ | -------------------------------------------- | -------------- |
| 表記ゆれ                       | 全角数字 `１０`、大小文字違い `a`、全角 `Ａ` | **受け入れる** |
| 貼り付け位置のずれ・無関係な値 | 氏名列を点数列へ貼った、`欠` など            | 弾いてトースト |

現在は `trim()` しかしていないため、`Number("１０")` が NaN になり、`a` は変換表の `A` と一致しない。これは間違いではなく表記の違いなので、**照合の直前に両側を正規化**（全角英数→半角、前後空白除去、文字評価は大小文字を無視）して受け入れる。

保存する値は正規化後のもの（文字評価なら**変換表のラベルそのもの**）にする。入力側だけを正規化すると、変換表のラベルが全角で登録されている場合に一致しなくなるため、**必ず両側へ同じ正規化を通す**。

### A-3 / A-4. タブに戻ってもプレビューが古いまま

#### 画面・機能

`/exams/[examId]/08-export`（結果出力）の右カードにあるタブ。

- **A-3 =「採点済み答案」タブ** ── 採点マークを重ねた答案画像のプレビュー
- **A-4 =「採点データ」タブ** ── Excel 出力の中身（設問別得点・小計・合計）のプレビュー表

どちらのプレビューも、**そのタブを開いている間だけ動く**（内部の `enabled` が「今このタブが選ばれているか」に直結している）。

#### 再現手順

1. 教員 P が `/exams/[examId]/08-export` を開き、「採点データ」タブでプレビュー表を確認する
2. P はその画面を開いたまま、別のタブ（「採点済み答案」など）へ切り替える
3. その間に、別の端末で採点が修正される（または P 自身が別ウィンドウで 05-students の学級配置・出席番号を直す）
4. P が「採点データ」タブへ戻る

#### いま起きること

手順 4 で**プレビューは手順 1 の内容のまま**。改修前は、タブを離れて戻るたびに読み直していた（内部の依存配列に「今このタブか」が含まれていた）。改修後は「試験と生徒選択が同じなら取得済み」とだけ判定するため、タブを往復しても取り直さない。

一方 **実際の出力ボタンはデータを読み直す**ので、教員が校正した表と配布される Excel／PDF の中身が食い違う。採点済み答案タブでは、直したはずの採点マークが古いまま見えるため「修正が消えた」と誤解して二度手間になる。

#### 修正後に起きること

タブへ戻るたびに読み直すので、プレビューと実際の出力が一致する。タブ内での操作（生徒の選び直しなど）では従来どおり無駄な再取得は起きない。

#### 手当て

タブ切り替えは `ExportOptionsCard` → `ExportMainView` に届く**ユーザー操作**なので、そこで再読込の合図を進める。

```tsx
const handleTabChange = (tab: ExportTabType) => {
  setExportTab(tab)
  // タブへ戻るたびにプレビューを読み直す
  // （出力は実データを読み直すので、プレビューと食い違わせない）
  setPreviewReloadKey((key) => key + 1)
}
```

この `previewReloadKey` を両プレビューへ渡し、「取得済みかどうか」の判定材料に加える。「タブへ戻ったら読み直す」という意図が、依存配列の副作用ではなく明示のコードになる。

## B. 元からある不具合（この差分とは無関係）

### B-1. 模範解答の並べ替えが、押した直後に元へ戻る

#### 画面・機能

`/exams/[examId]/01-upload`（模範解答アップロード）。各ページカードの **← / →** ボタンでページの順序を入れ替える。

#### 再現手順

1. 模範解答を3ページ以上アップロードする
2. 3ページ目のカードの **←** を押す

#### いま起きること

一覧が**押す前の並びに戻る**。新しい順序は DB へは書かれるが、画面上の各ページが持つページ番号は古いままで、一覧はそのページ番号で並べ直されるため。教員は効いていないと思って何度も押し、その都度違う並びが DB に書かれる。実際の順序は画面を開き直すまで分からない。

改修前も同じ再ソートが走っていたので、**今回入った不具合ではない**。

#### 修正後に起きること

押した瞬間に新しい並びで表示され、そのまま残る。

#### 手当て

親へ返す前に、手元のページ番号も振り直す。

```ts
const newAnswers = moveImageInList(answers, fromIndex, direction)
const renumbered = newAnswers.map((answer, index) => ({
  ...answer,
  pageNumber: index + 1,
}))
```

DB へ書く番号と手元の番号が一致するので、並べ替えが画面に残る。

### B-2. 生徒の一括登録で、入力した行が消える（原因は毎セルごとの全生徒再取得）

#### 画面・機能

`/students`（生徒マスタ管理）の「スプレッドシートからインポート」モーダル。表に貼り付け・入力し、**既に登録済みの学籍番号の行は赤く**表示される。

#### 手元にデータがあるのに取り直している

`/students` の画面本体（`StudentTable`）は、開いた時点で `fetchStudents()` の結果を `students` として**既に持っている**。ところがモーダルへはそれを渡しておらず（props は `isOpen` / `onClose` / `onImportSuccess` の3つだけ）、`useStudentImport` が自前で取り直している。しかも取り直しは**セルからフォーカスが外れるたび**に走り、1回の離脱で**2回**呼ばれる。

| 呼び出し元              | 目的                       | 頻度                         |
| ----------------------- | -------------------------- | ---------------------------- |
| `markDuplicateStudents` | 重複行に赤い印を付ける     | セルを離れるたび             |
| `validateStudentData`   | 「登録済みです」の警告文用 | セルを離れるたび（上とは別） |
| `handleImportStudents`  | 上書きか新規かの判定       | 登録実行時（これは妥当）     |

`fetchStudents` は**全生徒に全学級所属履歴（現在・過去の両方）を include** して返す。学籍番号の集合が欲しいだけの用途に対して、桁違いに重い問い合わせを1セルにつき2回投げている。

#### 再現手順

1. `/students` でインポートモーダルを開く
2. 1行目の学籍番号を入力し、Tab でセルを離れる
3. 続けてすぐ 2 行目の姓を入力し、Tab でセルを離れる

#### いま起きること

タイミングによって **2行目の入力が消える**。

問い合わせの結果が返るたびに、赤い印を付け直した**表の全行を丸ごと差し替えている**。この問い合わせには応答が投げた順に返る保証がないため、1行目の分（2行目をまだ含まない表を元にしている）が2行目の分より後に返ると、2行目の入力ごと巻き戻る。登録実行はこの表の内容を読むので、その生徒は無言で作成されない。

これは改修前から続く競合で、**根本原因は「毎セルごとに全件を取り直している」こと**にある。

#### 修正後に起きること

表の編集中の IPC 呼び出しが **0 回**になる。応答の追い越しが起きないので、入力が消えることもなくなる。

#### 手当て

親が既に持っている一覧をモーダルへ渡し、それを使う。実体をそのまま渡すので独自型は作らない。

```tsx
// StudentTable.tsx
<SpreadsheetImportModal
  isOpen={isSpreadsheetImportModalOpen}
  onClose={() => setIsSpreadsheetImportModalOpen(false)}
  onImportSuccess={onStudentsImported}
  existingStudents={students} // StudentWithMemberships[]（既に読み込み済み）
/>
```

`useStudentImport(existingStudents)` は受け取った一覧から学籍番号の集合を作って重複判定と警告文に使う。`handleImportStudents`（登録実行）の `fetchStudents()` は**書き込み直前に最新を見るべきなので残す**。

> モーダルを開いている間に他端末が同じ学籍番号を作った場合、赤い印は付かない。ただし登録実行時に最新を取り直して上書き／新規を判定するため、書き込み結果は正しくなる。

## C. 挙動差・堅牢化

### C-1. 画像パスが空のマスでスピナーが止まらない

#### 画面・機能

`/exams/[examId]/06-student-answers`（生徒答案管理）の表。各マスに答案画像のサムネイルが出る。

#### いま起きること

答案の画像パスが空文字のとき、「読み込み中」の判定は真になるのに、実際の読み込み処理は空文字を「パス無し」とみなして何もしない。結果、**回り続けるスピナー**が残り、読み込み中なのか答案が無いのかを見分けられない。

`StudentAnswerImage.imagePath` は必須列なので空文字が実際に入る余地は小さいが、2つの判定が食い違っていること自体が罠。

#### 修正後に起きること

空文字は「答案なし」のプレースホルダ表示になり、読み込み処理の判定と一致する。

#### 手当て

「読み込み中」の判定を、読み込み処理と同じ `!imagePath` に揃える（1箇所）。

---

### C-2. 一度読み込みに失敗した画像が、二度と読み直されない

#### 画面・機能

同じく `/exams/[examId]/06-student-answers`。答案の割り当てをドラッグで入れ替えながら、サムネイルで「どの答案が誰に付いたか」を目視確認する操作。

#### 再現手順

1. 大量アップロード中など、画像取得が一時的に失敗しやすい状況で表を開く
2. あるマスのサムネイルが読み込みに失敗する
3. その答案を別のマスへドラッグし、また元のマスへ戻す

#### いま起きること

**そのマスはセッション中ずっと空白のまま**。一度失敗したパスに失敗の印を付け、その印を消す経路が無いため。改修前は表示ソースが変わるたびに状態をリセットしていたので、手順 3 で読み直された。

#### 修正後に起きること（決定）

サムネイル表示の部分を子コンポーネントへ切り出し、**表示ソースを `key` にして作り直す**。

```tsx
<AnswerThumbnail key={previewUrl ?? imagePath ?? ""} ... />
```

表示ソースが変わるたびに子が作り直され、読み込み結果も失敗の印もまとめて捨てられる。改修前の「ソースが変わったら全部やり直す」へ完全復帰する。副産物として失敗の印は「今マウントされているこのソースが失敗したか」という単なる真偽値になり、**パスを覚えて突き合わせる必要も、消すタイミングを考える必要も無くなる**。

（「成功時に印を消す」案は1行で済むが、印をいつ消すかを考え続ける状態が残るため採らない。）

### C-3. 選択に戻した生徒へ、プレビューが勝手に戻る

#### 画面・機能

`/exams/[examId]/08-export` の個人成績表プレビュー。出力対象に選んだ生徒の中から**1人を選んでプレビュー表示**する。採点済み答案プレビューも同じ仕組みを共有している。

#### 再現手順

1. 生徒 B をプレビュー対象に選んで内容を確認する
2. B を出力対象から外す（プレビューは先頭の生徒 A に切り替わる）
3. A の成績表を確認している途中で、別の理由で B を出力対象に戻す

#### いま起きること

手順 3 で、**プレビューが操作なしに A から B へ跳ぶ**。「利用者が選んだ生徒」を捨てずに持ち続けているため。改修前は手順 2 の時点で B を捨てていた。

#### 修正後に起きること（決定）

**プレビュー対象が出力対象から外れたら、その選択自体を捨てて0番目にする。** 表示上は現状も0番目へ落ちるが、選択を覚えているため戻したときに跳ぶ。選択ごと置き換えれば跳ばない。

|        | 外れた直後  | その生徒を選択に戻したとき |
| ------ | ----------- | -------------------------- |
| 現状   | 0番目を表示 | **その生徒へ跳ぶ**         |
| 修正後 | 0番目を表示 | 0番目のまま動かない        |

#### 併せて直す: pick をタブ間で共通にする

現在 pick は**個人成績表用と採点済み答案用で別々の状態**になっており、タブを切り替えると別の生徒を見ている状態になりうる。`StudentSelectionCard` の生徒セレクタは1つしか無く、`previewType` でどちらの pick を読み書きするか分岐しているだけなので、**独立させる意味がない**（所有者判断）。

pick を `ExportMainView` の1つの状態へ持ち上げ、両プレビューへ引数として渡す。これにより次が消える。

- `StudentSelectionCard` の props 2本（`scoredAnswerPreviewStudentId` / `onScoredAnswerPreviewStudentChange`）
- 同カードの `Select` にある `previewType` による読み書きの分岐
- 各プレビューフックが pick を持つ責務（`setPreviewStudentId` の返却）

#### 手当て

「外れた瞬間に置き換える」を effect でやると B群に戻る。出力対象の増減は**すべて利用者の操作**なので、そちらで捨てる。統合後は pick が1つなので、捨てる処理も1箇所で済む。

```ts
// ExportMainView
const [pickedStudentId, setPickedStudentId] = useState<string | null>(null)
const previewStudentId =
  pickedStudentId && selectedExamStudentIds.includes(pickedStudentId)
    ? pickedStudentId
    : (selectedExamStudentIds[0] ?? null)
```

選択を変える3経路を包み、pick が対象から外れるなら捨てる。

- `toggleStudent(id)` ── 外す方向で、その id が pick なら捨てる
- `removeStudents(ids)` ── ids に pick が含まれるなら捨てる
- `replaceSelection(ids)` ── ids に pick が無いなら捨てる

捨てた後は上の導出が働いて0番目が表示される。

### C-4. 最終確認から戻るたびに、専属生徒数を数え直す

#### 画面・機能

学級を対象から外す2段階モーダル。

| 画面                                     | 用途                     |
| ---------------------------------------- | ------------------------ |
| `/grades/[gradeId]/02-students`          | 成績の対象学級           |
| `/coursework/[courseworkId]/02-students` | 試験外成績資料の対象学級 |

（`/exams/[examId]/05-students` は「登録解除のみ」の1段階モーダルなので該当しない）

1段階目で外し方（**登録解除のみ** / **専属の生徒も削除**）を選ぶ。後者を選ぶと「この学級にのみ所属する ◯名 が削除されます」と件数が出て、1名以上なら2段階目の取り消し不可の最終確認へ進む。

#### 再現手順

1. 学級行の削除ボタンを押す
2. 「登録を解除し、専属の生徒も削除」を選び「次へ」
3. 最終確認で「キャンセル」を押して1段階目へ戻る

#### いま起きること

手順 3 で**専属生徒数を数え直す問い合わせが再度走り**、「対象生徒数を確認中…」の表示と「次へ」の無効化が繰り返される。2段階目へ進むと1段階目の中身がアンマウントされ、件数が失われるため。破壊的操作の手前でためらうたびに名簿を再走査する無駄。

#### 修正後に起きること

2段階を往復しても件数はそのまま残り、待たされない。

#### 手当て

件数を、既に同じ理由で外側へ持ち上げてある「外し方の選択」の隣へ移し、**どの学級に対する件数か**を対で保持する。

```ts
const [preview, setPreview] = useState<{
  entry: ClassroomRosterEntry
  exclusiveCount: number
} | null>(null)
const exclusiveCount = preview?.entry === entry ? preview.exclusiveCount : null
```

取得は外側の effect（結果を `.then` で入れるだけなので同期 setState は無い）。対象の学級が変われば対で一致しなくなるので、前の学級の件数が残る心配もない。

## 満点超過の扱い（外部成績）── 決定済み

A-2 の調査中に「試験外成績資料は満点超過を許容していない」と一度結論したが、**これは誤りだった**。実データと方針を確認した結果を残す。

#### 方針（確定）

配点超え・負の点は**入力したとおり成績算出へ反映する**。頭打ちにしない。ボーナスや差し引きを、評価項目の満点という枠を超えて先生の裁量で乗せるための仕様。**例外は欠席者などの推定値のみ**で、これは従来どおり `0..満点` に収める（実際に付けた点と、機械が補った点で扱いを分ける）。

#### 実装の現状

| 入力経路                                          | 満点超過・負数 | 実態                                                |
| ------------------------------------------------- | -------------- | --------------------------------------------------- |
| 文字評価の変換表（`CourseworkLetterScale.score`） | **できる**     | 上限チェック無し。実データに S=30（満点20）あり     |
| 加減点列（`adjustment`）                          | **できる**     | 空欄 or 有限の数値なら有効                          |
| 素点列（`score`）                                 | **できない**   | `0 <= 値 <= 満点` で `validate` と保存の2箇所が拒否 |

成績算出側は方針どおり。`243d107e`（2026-07-01「試験外成績の配点超え・負値を成績算出にそのまま反映する」）で clamp を撤廃済みで、現在の `gradeCalculator` に clamp は無い。`absentEstimation` の clamp だけが残り、これが方針の言う推定値の例外にあたる。

#### なぜ素点列の不整合に気づかれなかったか

この制約は**数値入力の評価項目にしか効かない**。実データの評価項目は全て文字評価で、数値項目は 0 件、`score` 列が入った行も 0 件だった。満点超過は変換表（S=30 等）で実現されており、**素点列の上限には一度もぶつかっていない**。実害の出ていない不整合として残っていた。

#### 対応（決定）

素点列を**加減点列と同じ規則**（空欄 or 有限の数値なら有効。負数・満点超過を含む）へ揃える。

- `CourseworkScoresContainer.tsx` の `validate`（点数列）から `>= 0 && <= item.maxScore` を外す
- 同ファイルの保存分岐（「範囲外・無効値は無視」）から同じ条件を外す
- 列ヘッダ `(/${maxScore})` と placeholder `0-${maxScore}` は上限を示す表記なので、満点の目安を示す文言へ変更

これにより 04-scores で値が弾かれる場面は、**文字評価で変換表に無い記号**と、**数値列・加減点列への数値でない文字列**の2種類だけになる。
