# 所有と共有の設計（所有者 / 編集者 / 閲覧者）

対象: **#1127**。`docs/asb-ipc-split-plan.md` の段階4〜5 と、`docs/schema-relation-audit.md` §6.1 の前提。
検討日: 2026-08-03。着手は未定。

`docs/scoring-scope-and-permissions-design.md`（試験の採点範囲と権限）と対になる。あちらは
**試験のワークフローに固有の権限**、本書は**実体を誰が持ち誰と共有するか**という共通の枠組みを扱う。

---

## 1. なぜ今これが要るか

`AsbDefinition` を同期対象にした（`schema-relation-audit.md` §6.1）が、**利用者からは何も変わって
いない**。`listAsbDefinitions` が `where: { userId }` で所有者を絞るため、教員Aの定義は教員BのDBへ
複製されるのに B の一覧には現れない。定義本体と大問・小問・枝問・要素の全行が B のDBを占めるのに、
B からは存在しないのと同じ。

**共有の意図が UI 層で打ち消されている。** これを解くには「共有とは何か」を決める必要がある。

## 2. 現状（2026-08-03 実測）

### 2.1 所有の持ち方が機能ごとに全部違う

| 機能           | 所有の持ち方                          | 一覧の絞り込み                 | 共有の仕組み               |
| -------------- | ------------------------------------- | ------------------------------ | -------------------------- |
| 試験           | `UserExam`（`role` 付き中間テーブル） | `userExams.some({ userId })`   | **あり**（複数教員が参加） |
| 解答用紙作成   | `AsbDefinition.userId`（FK 一本）     | `where: { userId }`            | **無い**（単一所有者）     |
| 成績算出       | **列が無い**                          | 絞らない（`getAllGrades()`）   | 全員が全部見える           |
| 試験外成績資料 | **列が無い**                          | 絞らない（`getCourseworks()`） | 全員が全部見える           |

`Grade` と `Coursework` には所有者を表す列そのものが無い。**移行時に「誰のものか」を決める材料が
DB に無い**（→ §6.3）。

**この2つにも所有者は要る**（OWNER 裁定 2026-08-03）。全員が全部見える現状を仕様として追認せず、
解答用紙定義と同じメンバー制にする。

開発用DBの規模: `User` 2件 / `Grade` 3件 / `Coursework` 4件 / `Exam` 31件 / `UserExam` 31件。

### 2.2 `UserExam.role` は既に2ロール制で、意識的にそう決めてある

```prisma
model UserExam {
  role      String @default("GRADER") // "OWNER" | "GRADER"
  invitedAt DateTime @default(now())
  invitedBy String?  // Null for OWNER (exam creator)
  @@unique([userId, examId])
}
```

`docs/scoring-scope-and-permissions-design.md` §3-3 が、段階ごとのスイッチ案と比較したうえで
2ロールを選んでいる。

> **GRADER は 07 のみ。準備段階（01-06）をさせたいなら OWNER に昇格する。**
> 段階ごとのスイッチを**全段階に対して**作る案（`UserExam` に Boolean 3本等）とは比べた結果、採らない

この切り方には理由がある。**匿名採点を壊すのは 05・06・08 だけ**なので、GRADER を 07 に閉じ込めると
匿名性が自動的に成立する。ロールの強度ではなく**ワークフローのどの段に入れるか**で切ってある。

### 2.3 【訂正】main は誰がログインしているかを知っている

`docs/asb-ipc-split-plan.md` の初版と検討の途上で「main は誰がログインしているか知らない」と
書いたが、**これは誤り**。認証ストア経由で取得できる。

```ts
// electron-src/lib/prisma/auditActor.ts
export function getCurrentActorUserId(): string | null {
  // 認証トークンは userId そのもの（AuthContext がトークン = userId として扱う）
  return AuthStoreManager.getAuthToken()
}
```

ログイン時に renderer が `saveAuthToken(selectedUser.id)` を呼び（`AuthContext.tsx:74`）、
main の `AuthStoreManager` が保持する。監査ログの操作者記録は既にこの経路で動いている。

**したがって権限判定を main に置くことは今すぐできる。** 認証の作り込みは前提ではない。

### 2.4 ただし `getCurrentUser()` は暫定実装のまま残っている

```ts
// electron-src/lib/prisma/user.ts:16-25
export const getCurrentUser = async (): Promise<User | null> => {
  // TODO: Implement actual current user retrieval logic
  return await prisma.user.findFirst() // ← 最初の1人を返すだけ
}
```

`User` テーブルは同期対象なので、同期が始まると各端末のDBに全教員の User 行が入る。`findFirst` が
返すユーザーは端末ごと・同期ごとに変わりうる。

**これは将来の問題ではなく現在の不具合である。** 呼び出し元は3箇所:

| 箇所                                                           | 使われ方                                             |
| -------------------------------------------------------------- | ---------------------------------------------------- |
| `src/components/exams/02-template/hooks/useTemplateData.ts:71` | **主経路**。`currentUser` として採点領域の保存に渡る |
| `src/app/exams/[examId]/03-region-info/page.tsx:55`            | 主経路                                               |
| `useScoringDataLoader.ts:65`                                   | `AuthContext` の id が無いときのフォールバック       |

02-template と 03-region-info は、**複数ユーザーが居ると別人として記録されうる**。
`getCurrentActorUserId()` へ差し替えれば直る（§5）。

### 2.5 これは権限境界ではない

`scoring-scope-and-permissions-design.md` §2-4 の前提を、本書もそのまま引き継ぐ。

> ローカルインストール＋NAS 共有で、GRADER の手元に DB ファイルそのものがある。
> URL 直打ちや DB 直読みは止められない。
> 得られるのは「**採点者の作業導線から採点以外を外す**」であって「見せない」ではない。
> UI 文言もこの範囲で書く。「アクセスを禁止します」は過剰約束。

3ロールも同じ性質のものである。**事故防止と見通しのための仕組みであって、秘匿の仕組みではない。**
UI 文言は「編集できません」までにとどめ、「見られません」と書かない。

## 3. モデル

### 3.1 3ロール

| ロール            | 一覧に出る | 開く | 内容を変える | メンバーを変える | 実体を消す |
| ----------------- | ---------- | ---- | ------------ | ---------------- | ---------- |
| **所有者** OWNER  | ✅         | ✅   | ✅           | ✅               | ✅         |
| **編集者** EDITOR | ✅         | ✅   | ✅           | ✗                | ✗          |
| **閲覧者** VIEWER | ✅         | ✅   | ✗            | ✗                | ✗          |
| （メンバー外）    | ✗          | △    | ✗            | ✗                | ✗          |

**この3つを全実体で使う。** 解答用紙定義・成績算出・試験外成績資料に加え、試験も同じ語彙へ
再分類する（§4.6）。

「メンバー外が開ける（△）」のは、id を直接指定する取得経路にメンバー判定を入れない場合の話。
§2.5 のとおり秘匿は目的ではないので、**一覧に出さないことを主とし、単体取得を塞ぐかは別途決める**。

**所有者は複数可**とする。試験側で「OWNER 2人（学年運用型）」を扱う必要が既に判明しており
（`scoring-scope-and-permissions-design.md` §0 パターンB）、単数前提にすると同じ壁に当たる。
ただし**最後の1人の所有者は降格・削除できない**（孤児化の防止。試験側の `removeExamMember` が
同じ罠を持っていて、§6 実装上の罠に挙がっている）。

### 3.2 現行の試験ロール（`GRADER`）はどこに入るか

**`GRADER` は編集者でも閲覧者でもない。**

- 試験の**構成**（設問・配点・名簿）は変えられない → 編集者ではない
- 採点結果は**書く** → 閲覧者でもない

3ロールへ機械的に寄せると置き場所が無くなり、押し込めば匿名採点の根拠（07 だけに閉じている）が
壊れる。

素直に重なるのは、**権限の対象を「試験」ではなく「試験の構成」と「採点データ」の2つと見る**読み方
である。

| 現行ロール | 試験の構成（01-06）                | 採点データ（07） |
| ---------- | ---------------------------------- | ---------------- |
| `OWNER`    | 編集者                             | 編集者           |
| `GRADER`   | **閲覧者**（実際には導線から外す） | **編集者**       |

現行の2ロールは、3ロールを2つの対象に適用した結果の**名前付きプリセット**だった、という整理になる。
再分類（§4.6）はこの表を出発点にできる。

**ただし対象が2つある構造自体は3ロール化では消えない。** 1人が対象ごとに違うロールを持つのを
「ロール1つ＋フラグ」で畳むか「対象ごとにロール」で表すかが #1071 の宿題になる（→ §4.6）。

### 3.3 ロールに乗らない能力はフラグで足す

試験側は既にこの形になっている。

| 能力                     | 表現                            |
| ------------------------ | ------------------------------- |
| 08（結果出力）を使える   | `UserExam.canExportResults`     |
| 匿名採点を試験単位で強制 | `Exam.anonymousScoringEnforced` |

**ロールを増やして表現しようとしない。** ロールは「どれだけ変えられるか」だけを表し、機能固有の
可否はフラグにする。ロールが4つ5つに増えると、どのロールに何が付くかを覚えられなくなる。

## 4. スキーマ

### 4.1 メンバーテーブル

`UserExam` に倣い、実体ごとに中間テーブルを置く。

```prisma
model AsbDefinitionMember {
  id              String   @id @default(uuid())
  asbDefinitionId String
  userId          String
  /// "OWNER" | "EDITOR" | "VIEWER"
  role            String   @default("VIEWER")
  invitedAt       DateTime @default(now())
  /// 招待した人。所有者を最初に作るときは null
  invitedBy       String?
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  asbDefinition AsbDefinition @relation(fields: [asbDefinitionId], references: [id], onDelete: Cascade)
  user          User          @relation(fields: [userId], references: [id], onDelete: Cascade)
  inviter       User?         @relation("AsbDefinitionMemberInviter", fields: [invitedBy], references: [id], onDelete: SetNull)

  @@unique([asbDefinitionId, userId])
  @@index([asbDefinitionId])
  @@index([userId])
}
```

`GradeMember` / `CourseworkMember` も同形。

### 4.2 id は uuidv4、同定は `@@unique`

2端末が同じ人を同じ資料に追加すると id 違い・`@@unique` 同値の行が2つできるが、**これは
sqlite-nas-sync が解決する**（`conflict.ts` の `applyInsert` が `updatedAt` の LWW で敗者行を
削除し、1行へ収束させる）。id を親子キーから組み立てる必要はない。

> 当初は #1128 に倣って「新設の時点で決定論的 id にする」方針だったが、その #1128 自体が
> ライブラリの挙動を誤認していたため撤回された（2026-08-03）。メンバーは**付け外しする**ので、
> 決定論的 id にすると「過去の削除 tombstone が未来の同じ組み合わせを撃つ」「別端末の追加が
> 他端末の削除に吸収される」という混線を買うことになり、むしろ有害だった。

**書き込みは必ず `@@unique` を鍵に upsert すること。** id は端末ごとに異なるので同定に使えない。
`@@unique` を持つ中間テーブルを新規に作るときは、これを既定の作法とする。

### 4.3 role の表記は大文字

**`OWNER` / `EDITOR` / `VIEWER`**（OWNER 裁定 2026-08-03）。

`ExamStudent.status` は #1117 で小文字へ統一した経緯があり、当初は新設分も小文字にする案だった。
これを採らないのは、**試験も同じ3ロールへ再分類する**（§4.6）ため。同じ語彙を全実体で使うなら、
`UserExam.role` の既存値（`OWNER`）と揃う大文字の方が値の移行が要らない。

ステータス列（小文字）とロール列（大文字）で表記が分かれるが、**別の語彙なので混ざらない**。

### 4.4 ユーザー削除は仕様。カスケードは一律 `Cascade`

**裁定（OWNER 2026-08-03）**

- **ユーザーを削除したらそのユーザーのデータも消える。これが仕様。** Google Workspace と同じ
- **カスケードが無くて残骸が残る方が問題。** 全テーブル一律 `onDelete: Cascade`
- **現状の問題は、ユーザー削除機能が無いこと**（`deleteUser` に相当する関数・IPC・UI が存在しない）

実装は **#1140** で行う。本節はその設計根拠を持つ。

#### 現状は一律ではない（2026-08-03 実測）

`User` を参照する11のリレーションは3種類に分かれている。

| 削除挙動       | モデル                                                                                    | 現状の帰結                   |
| -------------- | ----------------------------------------------------------------------------------------- | ---------------------------- |
| `Cascade`      | `AsbDefinition` `UserExam` `CropRegionAssignment` `UserKeyboardShortcut` `UserPreference` | 仕様どおり消える             |
| **`NoAction`** | **`QuestionScore` `ScoreDecision` `CompoundAnswerScore`**                                 | **削除が FK 違反で失敗する** |
| `SetNull`      | `CropRegionAssignment.assignedBy` `UserExam.invitedBy` `GradeFrozenScore.frozenByUserId`  | 実行者が不明になる           |

**採点系3つが `NoAction` かつ `NOT NULL`** なので、**一度でも採点したユーザーは削除できない**。
削除機能を実装しても、実運用のユーザーはまず消せない。開発用DBでは `QuestionScore` が
**68,967件あり、すべて同一ユーザー**である。

#### 直すこと

`QuestionScore` / `ScoreDecision` / `CompoundAnswerScore` の `onDelete: NoAction` を `Cascade` へ。
これで裁定どおり「消したら消える」が成立する。

> **⚠️ 確認が要る点 — nullable な実行者参照3つ**
>
> `assignedBy` / `invitedBy` / `frozenByUserId` は「誰がやったか」の記録で、いずれも nullable。
> ここを `Cascade` にすると帰結が変わる。
>
> **教員Aが教員Bを試験に招待したあと A を削除すると、B の `UserExam` 行が消えて B が試験から
> 外れる。** 消えたのは A なのに、影響を受けるのは B である。`assignedBy`（担当を割り当てた人）も
> 同じ形になる。
>
> 残骸ではなく「実行者が不明になるだけ」なので、この3つは `SetNull` のままにするのが妥当だと
> 考える。**別段の指示が無ければ、この3つのみ `SetNull` を維持して書く。**

#### 削除操作そのものに要る手当て

Workspace は削除時にデータが消える点は同じだが、**削除の前に所有権の移管ツールを挟み、
20日間の復元期間を置いている**。消えること自体より、消える前に何が消えるかを見せることが本体である。

- **確認ダイアログで件数を出す。** 「この教員を削除すると、採点結果 68,967件・解答用紙 12件が
  消えます」。`MasterImage` を畳んだときの削除ダイアログ（答案の件数を示す）で確立した形と同じ
- **同期経由で全端末へ伝播する。** ローカルで消すと tombstone が他端末へ届き、そちらでも消える。
  **取り消せない**。ダイアログはこのことも伝える
- **移管の導線を検討する。** 採点結果は生徒に紐づく資産でもある。削除の前に別の教員へ付け替える
  選択肢があると、Workspace と同じ体験になる。**これは削除機能の issue で扱う**

### 4.5 `AsbDefinition.userId` は名前も Cascade も変えない

```prisma
user User @relation(fields: [userId], references: [id], onDelete: Cascade)
```

**このまま維持する**（OWNER 裁定 2026-08-03）。列名を `createdBy` へ改名する案も、
`onDelete: SetNull` へ緩める案も採らない。ロール判定はメンバー表が持ち、`userId` は作成者の記録として
そのまま残る。

> **⚠️ 2026-08-03 訂正**
>
> 本節は当初「教員のアカウントを消すとその人の解答用紙が全部消えるので Cascade を外す」と
> 書いていた。**誤り。**
>
> - **消えること自体が仕様**（§4.4）。「消えるのは困る」を根拠にしていたのが誤り
> - **ユーザーを削除する経路が現時点で存在しない。** `deleteUser` に相当する関数・IPC・UI が
>   いずれも無い（`electron-src/lib/prisma/user.ts` にあるのは `fetchUsers` / `getCurrentUser` /
>   `createUser` 等）。到達不能な状態を根拠にしていた
> - **緩める方が危険。** `SetNull` にすると、作成者が消えた定義が残る。メンバー行は
>   `AsbDefinitionMember.user` の Cascade で一緒に消えるので、**誰のメンバー行も無い定義**が
>   出来上がる。§3.1 のとおり一覧はメンバー行で絞るので、これは**誰からも見えず消せない行**になる。
>   この試験が2度潰した形（`MasterImage` の幽霊ページ、`GradeBoundarySet` の空セット）と同じ

**作成者Aの定義に編集者Bが居る場合も、A の削除で定義ごと消える。** これは §4.4 の裁定に沿った
挙動である。B にとっては予告なく消えることになるので、**削除ダイアログで影響範囲を出す**
（§4.4 の「削除操作そのものに要る手当て」）。

### 4.6 試験も3ロールへ再分類する（設計は #1071）

**方針は決まっている**（OWNER 裁定 2026-08-03）。`OWNER` / `GRADER` の2ロールを
`OWNER` / `EDITOR` / `VIEWER` へ再分類する。ただし**設計は #1071 で行い、本書では実装しない**。

理由は、試験のロールが `scoring-scope-and-permissions-design.md` の設計（段階アクセス・匿名採点・
担当割当）と一体で単独では動かせないこと、`transferOwnership` / `removeExamMember` /
`canExportResults` が絡むことによる。

#### #1071 が解く必要のある点

**`GRADER` は `EDITOR` へ寄る**（採点データを書くので閲覧者ではない）。しかし
「01-06 に入れない」はロールの強度では表せない。ここが宿題になる。

| 論点                                  | 内容                                                                                                                                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 「準備段階に入れない」の表現          | §3.3 の方針に従えばフラグ。ただし `scoring-scope-and-permissions-design.md` §3-3 は「段階ごとのスイッチ」を一度**却下している**。3ロール化はその判断の再検討を含む |
| 匿名採点の根拠を保てるか              | 同 §3-3 は「GRADER を 07 に閉じ込めれば匿名性が自動的に成立する」ことを2ロールの根拠にしていた。3ロールでもこの性質を保つ必要がある                                |
| `VIEWER` と `canExportResults` の重複 | 「採点はしないが結果を見る人」は `VIEWER` そのもの。3ロール化で `canExportResults` の一部がロールに吸収されうる                                                    |
| 昇格・降格の経路                      | ロールが3つになると `transferOwnership`（OWNER 常に1人前提）の見直しが要る。**最後の1人の OWNER を降格できない**規則も同時に入れる                                 |

#### 対象が2つある問題は残る

§3.2 のとおり、試験には「構成（01-06）」と「採点データ（07）」という**2つの対象**がある。
ロールを3つにしても、1人が対象ごとに違うロールを持つ構造は消えない。#1071 は
「ロール1つ＋フラグ」と「対象ごとにロール」のどちらで表すかを決めることになる。

## 5. 前提作業：現在ユーザーの一本化

ロール判定を main に置くには、main が「今の操作者」を1つの経路で得られる必要がある。
§2.3 のとおり経路は既にあるので、**暫定実装を差し替えるだけで済む**。

1. `getCurrentUser()`（`user.ts:16`）を `getCurrentActorUserId()` 経由の実装へ差し替える
   （`findFirst()` を捨てる）
2. `auditActor.ts` の `getCurrentActorUserId` を `prisma/` の外へ出すか、`user.ts` から呼ぶ形にする
   （現在は監査ログ専用の位置にある）
3. 認証ストアが空（未ログイン・テスト環境）のときの扱いを決める。監査ログは `null` を許して
   「システム操作」としているが、**ロール判定で `null` を許すと誰でも通ってしまう**。
   権限判定側は「不明なら拒否」にする

**この3点は3ロールの前でも単独で価値がある**（§2.4 の 02-template / 03-region-info の誤記録が直る）。

## 6. 移行

### 6.1 原則：今見えているものを見えなくしない

| 機能           | 現状             | 移行で作る行                                                         |
| -------------- | ---------------- | -------------------------------------------------------------------- |
| 解答用紙作成   | 所有者のみ見える | `userId` の人を `OWNER` として1行                                    |
| 成績算出       | **全員見える**   | **全ユーザー × 全 Grade**。最古のユーザーを `OWNER`、残りを `EDITOR` |
| 試験外成績資料 | **全員見える**   | 同上（`Coursework`）                                                 |

成績算出・試験外成績資料でメンバー表を入れると、**入れた瞬間に他の教員から見えなくなる**。
現状を保つには全組み合わせを作るしかない。開発用DBの規模なら 2×3 + 2×4 = 14行で済む。

### 6.1.1 所有者は「最古のユーザー」を暫定で立てる（OWNER 裁定 2026-08-03）

**所有者ゼロで出発しない。** `Grade` / `Coursework` は誰のものか DB から分からない（§2.1）が、
所有者が1人も居ない実体は**行き止まり**になる — メンバー変更も削除も所有者にしかできないので、
誰もそこへ到達できない。逃げ道を UI に用意するより、**その状態を作らない**方が確実である。

移行時点で最も古い `User` を暫定の所有者とする。

```sql
-- 最古のユーザーを OWNER、それ以外を EDITOR にする
INSERT INTO "GradeMember" ("id", "gradeId", "userId", "role", ...)
SELECT
  "Grade"."id" || ':' || "User"."id",
  "Grade"."id",
  "User"."id",
  CASE WHEN "User"."id" = (
    SELECT "id" FROM "User" ORDER BY "createdAt" ASC, "id" ASC LIMIT 1
  ) THEN 'OWNER' ELSE 'EDITOR' END,
  ...
FROM "Grade" CROSS JOIN "User";
```

**順序は `createdAt ASC, id ASC`**（`User.createdAt` は存在する）。rowid や挿入順に依存しない —
序数を同定に使わないという既存規約に従う。実測でも最古のユーザーは導入した本人だった。

これは「誰が作ったかの推測」ではなく、**明示された既定値**である。§6.3 の監査ログ推測を退けたのは
「知っているふりをする」ためで、既定値を置くこと自体は問題ない。§2.5 のとおり権限境界ではないので、
外れていても UI から所有者を足す・移すだけで済む。

#### 端末ごとに移行が走るので、所有者が2人になりうる

マイグレーションは端末ごとにローカルDBへ適用される。同期前に走った端末と同期後に走った端末とで
`User` の集合が違えば、**「最古のユーザー」も違う**。両方のメンバー行が同期で合流すると、同じ実体に
`OWNER` が2人できる。

**これは壊れではない。** §3.1 のとおり所有者は複数可。合流しても行 id は
`${entityId}:${userId}` で決まるので重複行にはならず、増えるのは所有者の人数だけである。

### 6.2 移行後に増えたユーザーは自動では入らない

今日は新しい教員を作ればその瞬間に全成績が見える。メンバー制ではそうならない。
**これは意図した挙動の変化**だが、移行直後に「新人が何も見えない」と驚かれる形で出る。

対応は2択。UI で「全員を追加」を一発でできるようにするか、`Grade` に「全員に公開」フラグを持つか。
**前者を推す** — フラグを足すとロールと二重の判定軸になり、§3.3 の方針に反する。

### 6.3 作成者を監査ログから復元しようとはしない

`Grade` / `Coursework` に所有者列が無いため、作成者を知る手段は監査ログしかない。
`AuditLog` には `grade.create` / `coursework.create` が `userId` 付きで残っている（実測: 5件すべて
`userId` 非 null）。監査ログの操作者は `getCurrentActorUserId()`（認証ストア）で記録されており、
§2.4 の `getCurrentUser()` とは別経路なので**値そのものは信用できる**。

**それでも採用しない。**

- 監査ログは保持期間で消えうる。全件について作成記録が残っている保証が無い。残っている実体と
  残っていない実体で移行の挙動が変わる
- 「たぶんこの人が作った」と推測して所有者を決めると、**間違っていても誰も気づけない**。
  推測が当たっているように見えるぶん、外れたときに疑われない

§6.1.1 の「最古のユーザー」と何が違うかというと、**推測しているかどうか**である。前者は
「作成者は分からないので、導入した人を既定の所有者に置く」と宣言しており、外れることが前提に
なっている。監査ログ推測は「作成者が分かる」という顔をして外れる。

## 7. 一覧と導線

- 一覧はメンバー行のある実体だけを返す（`some({ userId })`）
- **ロールは一覧に表示する。** 開いてから「編集できない」と分かるのは事故のもと
- 閲覧者で開いたときは編集 UI を出さない。§2.5 のとおり文言は「編集できません」まで
- メンバー管理 UI は試験の `MemberInviteDialog`（`layout.tsx:107`）が既にあるので、実体を問わず
  使える形に一般化するのが自然

## 8. アーカイブ

**メンバー行はアーカイブを越えない。** `UserExam` が既にそうしており（`dataCollector.ts:532` で
`userExams: []`、インポートは現ユーザーを OWNER として1件作る）、同じ扱いにする。

理由は、ユーザーの集合が導入先ごとに違うため。持ち込んでも参照先の `User` が無い。

**帰結: メンバーテーブルを足してもアーカイブの改版が要らない。** インポートは取り込んだ人を
`OWNER` として1行作る。
