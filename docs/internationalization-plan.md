# 国際化の計画

**これは段階表に載せない。** 他に優先することが多く、着手時期は未定である
（2026-08-23 に OWNER 決定）。[remaining-work.md](./remaining-work.md) の段階として
番号を振るのは、**実際に着手すると決めたとき**にする。

**この文書は「やるかどうか」を論じるものではなく、やると決めたときの手順を書いたもの
である。** §6 は「翻訳しても海外からの流入は増えない」ことを数字で示すが、
**それはやらない理由ではない。** 多言語対応の主な効果は海外の獲得ではなく、
**国内の利用者に対して標準に載っていることを示すこと**にある（§6 末尾）。
**費用対効果の節だけを読んで「やめる」と結論しないこと。**

## 要点

- **構造は既に国非依存だった。** 学級も評定も日本の制度を前提にしておらず、
  それは大学教員が使えていることで既に実証されている（§2）
- **実作業は氏名まわりと文言の抽出だけ**（§3）
- **ただし翻訳しても利用者は増えない。** いまの流入はホームページと口コミで、
  **口コミは言語を越えない**（§6）
- **だから「海外の利用者が増える」ことは期待しない。** 流入を増やす手としては
  国内施策の方が期待値が大きい。**多言語対応の効果は §6 末尾の方にある**

## 2. 最初の見立ては誤り — 構造は既に国非依存だった

**「学級が日本固有だから、成績算出は丸ごと国別になる」と最初に書いたが、スキーマを読むと
違った。**

- `Classroom` は**教科も担任も時限も持たない**。「名前のついた生徒の集まり」以上のことを
  主張していない（`grade` も `classroomCode` も nullable、`name` に `@unique` も無い）
- `StudentClassroomMembership` は `startDate`/`endDate` を持つ多対多。**1人が同時に複数
  所属できる** — 米国の生徒が6つの course section に居るのは membership が6本あるだけ
- `attendanceNumber` は Student でなく **membership 側にあって nullable**。出席番号が無い
  国では null
- `ExamClassroom` の3スイッチ（`administered` / `teacherStatistics` / `studentReport`）は
  「どの集団で採番するか」「どの集団を平均するか」「どの集団と比べるか」を独立に持つ。
  **日本の学級が要求するより一段一般的**
- `GradeItemBoundary` は `label` が自由文字列・`minPercentage` が Decimal で、**段数も向きも
  固定していない**。ドイツの 1〜6（1が最高）も英国 GCSE の 9〜1 もフランスの /20 も、
  設定を入れるだけで入る

**決定打は、大学教員が既に使っていること。** 日本の大学は固定学級なし・出席番号なし・
担任なし・評定は秀優良可不可／GPA で、構造は米国の高校と同じである。つまり
**「英米型の course-based が乗るか」は本番で既に検証済み**だった。

`年度` を grep しても出てくるのは UI ラベルとヘルプ文だけで、`getMonth() < 4` のような
年度計算はどこにも無い。`enrollmentYear` はただの `Int?` である。**4月始まりも構造では
なく文字列だった。**

## 3. やること

**この順序に意味がある。** 上ほど i18n と独立に価値があり、下ほど §6 の入口が無いと
効かない。

### 3-a. エラーのコード化（**i18n と無関係に、いま効く**）

`electron-src` の748行の日本語エラーメッセージに、言語に依存しない識別子を与える。

```
❌ 「読み込みに失敗しました」   ← 同じ文面が複数箇所にあり、どこで落ちたか特定できない
✅ E-IMPORT-0042              ← 一意に指せる
```

**報告経路が Discord なので、ここが一番効く。** 来るのは「エラーが出ました」とスクショで
あり、文面が日本語でも英語でも、**同じ文言が複数箇所にあれば特定できない**。日本語の
サポートでいま困っていることが、そのまま解ける。

併せて、main にカタログを置かず **IPC でコードを返して renderer 側で文言化する**形にする。
これは「計算は renderer 側」と同じ向きで、i18n をやるかどうかと関係なく正しい。

### 3-b. 氏名の日本語前提を外す

```prisma
model Student {
  lastName      String  // NOT NULL — 姓を持たない文化が入らない
  firstName     String
  lastNameKana  String  // NOT NULL — 日本語専用
  firstNameKana String
}
```

**国外向けの話ではなく、いまの問題である。** 日本の大学の留学生でカナが埋まらず、
NOT NULL なので**何かを入れさせている**。

1. **姓名順の直書き43箇所を1つの整形関数へ寄せる。** 名前の順序を知っているのは
   その関数だけにする（`RosterTable.tsx`・`useStudentAddPanel.ts` などが、それぞれ独自に
   `fullName` を組み立てている）
2. `lastNameKana` / `firstNameKana` を nullable にする migration
3. カナが無いときの検索・表示のふるまいを決める（いまは必ずあると仮定している）

**注意** — 検索が `${lastNameKana} ${firstNameKana}` を組み立てている箇所がある。
null で `"undefined undefined"` を作らないこと。また**アーカイブ側の型も nullable になる**
ので、`examArchive` / `courseworkArchive` の版を上げてトランスフォーマーが要る
（[CLAUDE.md](../CLAUDE.md) §スキーマ変更時のImport/Export対応ルール）。

**1 だけなら単体で入れられる。** i18n を見送っても、43箇所が1つに寄るのは正しい整理である。

### 3-c. 英語の README とホームページ

**口コミに依存しない唯一の入口**（§6）。開発者は GitHub で物を見つけるので、
ここだけは翻訳が流入に直結する。**UI の翻訳と切り離して先に出せる。**

### 3-d. UI の文言をカタログへ出し、`en.json` まで作る

1. 抽出と `t()` 化の機構
2. `ja.json` は抽出結果をそのまま置く
3. **`en.json` は自分で（LLM で）出す。** 2,073文字列は数時間の作業であり、
   **コントリビュータを待つ理由が無い**（§4 で撤回した項目）
4. `'ja-JP'` 直書き33件と `toLocale*` 19件を `Intl` へ寄せる

## 4. やらないこと

- **ソースコメント16,290行の英語化はしない**（**OWNER 決定・2026-08-23**）。
  読みたい人が各自 LLM で訳せば足りる。英語コメントを成果物として持つと必ず日本語側と
  ズレるので、**一次情報は日本語1本に保つ**
- **帳票レイアウトの国別化はしない。** Excel の学級平均行は `teacherStatistics` で切れる
- 縦書き27箇所と原稿用紙は、使わない国では使われないだけなので何もしない
- 姓名順を利用者が切り替えられるようにする。**3-b で関数1つに寄せておけば後から足せる**

**撤回した項目** — 当初「他言語カタログは自分で書かない、訳すのはコントリビュータの仕事」
と書いたが、**訳文の提供を外部に期待しない方針とする**（OWNER・2026-08-23）。
2,073文字列の英訳は LLM で数時間の作業であり、待つ必要が無い。`en.json` は自分で出す（3-d）。

## 6. 流入の構造 — これは「海外の利用者を増やす手」ではない

いまの流入は**ホームページと口コミ**である。

**口コミは言語を越えない。** 日本語教員 → 日本語教員のチェーンでしか伝わらないので、
韓国の教員には届かない。

```
日本  ホームページ → 口コミ → 口コミ → ...   ← 連鎖が回っている
韓国  （入口が無い）                          ← en.json があっても誰も来ない
```

**UI を訳しても、それ単体では流入は1件も増えない。** 増えるのは「たどり着いた人が
使い続けられる確率」だけである。ファネルの下流を広げても、上流に水が来ていなければ量は
変わらない。海外で口コミの種火を作るには、その国に最初の数人が要る。そこが一番高い
コストで、翻訳とは別物である。

**そして国内の到達余地が桁で残っている。** 日本の中高教員はおよそ47万人（概数）で、
現在の利用者数とは2桁の開きがある。**国内では口コミの連鎖が既に回っており、言語の壁も
無い。** 流入を増やす手として同じ時間を投じるなら、期待値は国内の方が明らかに大きい。

**目的の訂正** — 当初は「コントリビュータ確保」を理由に挙げたが、報告経路が Discord で
ある以上、外国利用者は**コントリビュータではなく報告対象**になる。得られるのは
バグ報告（＝品質）であって、実装の手ではない。この非対称を踏まえると、
**流入を増やす手としては、UI 翻訳より 3-a（エラーコード）と 3-c（英語の入口）が先に効く。**

### ただし、翻訳には国内向けの効果がある

**言語切り替えが在ること自体が、日本の利用者に対するメッセージになる**
（OWNER・2026-08-23）。「グローバルスタンダードに載っている」「ちゃんとした製品である」
という印象は、**国内の口コミの質に効く**。上の議論は「海外からの流入」だけを数えており、
**この経路を勘定に入れていない。**

有償の競合が並ぶ市場では、導入を検討する側は短時間で製品の成熟度を判断する。
多言語対応は、機能の多寡とは別の軸で**開発の本気度を一目で示せる**数少ない手段である。

## 7. 海外市場の下調べ（2026-08-23）

**主戦場である中高には、海外に同型の競合がほぼいない。**

### 価格（公開されているもの）

| 製品                        | 価格                                                                               | 単位           | 対象         |
| --------------------------- | ---------------------------------------------------------------------------------- | -------------- | ------------ |
| **ZipGrade**                | 無料（月100枚）／**$6.99・1年**                                                    | 教員1人        | 中高・選択式 |
| **Gradient**（旧 GradeCam） | Teacher Basic **無料**（10問まで）／Plus **$150/年**／学校・学区 **$3.00/生徒/年** | 生徒数         | **K-12専業** |
| **Akindi**                  | 非公開。**年間採点枚数ベース**の年額。30日無料パイロット                           | 採点した答案数 | 大学中心     |
| **Gradescope**              | **Basic 無料**（機関トライアル終了後も継続可）／Institutional は**非公開**         | 生徒数         | 大学中心     |
| **Crowdmark**               | **非公開**。年額またはコース単位、教員／学部単位でライセンス可                     | 利用者数       | 大学中心     |
| **Remark Office OMR**       | 買い切り。公開価格なし                                                             | 単体＋サイト   | 汎用         |

**記述式まで扱う製品は全部が非公開・商談ベースで、公開価格があるのは選択式専用の
安い製品だけ**（ZipGrade $7/年、Gradient $3/生徒/年）。ここに市場の構造が出ている。

※ 第三者集計サイトの「Gradescope $1〜3/生徒」は公式ではない。Remark の
「Rs 65,000」は2012年のインド代理店価格で、現在の参考にならない。

### 普及率

**Gradescope**（この分野で唯一まともな数字が出ている）:

- **教員 140,000人／生徒 320万人／2,600機関**、累計 **7億問**
- **アイビーリーグの半数**、R1大学25校以上（Purdue・CMU など）
- Turnitin 全体では16,000機関。日本は Turnitin 製品を200機関以上（2010年以降）

**完全に高等教育の数字である。** 中高の内訳は公表されていない。

### 中高に競合がいない理由

1. 欧米の中等教育では**日常のテストが選択式**か、記述は個別課題として LMS
   （Canvas・Google Classroom）で1人ずつ採点する
2. **高stakes の記述式は学校が採点しない。** 英国の GCSE / A-level は試験団体
   （AQA・Pearson・OCR）が答案を集約し **RM Assessor** で処理する業務システム
3. 結果、**学校向けに残るのはマークシートだけ**なので、安い製品しか無い

新興の AI 採点（GradeLab・GRADED+・PaperScorer）が手書きに手を出し始めているが、
**インド系が目立つ**。大量の紙試験が残っている市場だからで、これは示唆的である。

### 注意すべき事実

**Gradescope には日本語正式版がある。** 2021年9月にパイロット、**2022年3月に正式提供**
（英語・スペイン語・韓国語・トルコ語と並んで日本語）。**既に日本市場に入っている。**
ただし浸透しているのは大学で、中高では見えない。

### そこから読めること

- 一括採点の主戦場は**海外に同型の競合がいない領域**だが、それは
  **市場が無いから誰も作っていない**可能性を含む
- 翻訳が効きそうなのは欧米の中高ではなく、**①東アジア（韓国・台湾・中国＝紙の記述式
  文化が同じ・固定学級もある）②大学（ただし Gradescope が先行）③インド**
- **利用者を増やす言語（韓国語・中国語）と、開発者を呼ぶ言語（英語）は別物である**

## 8. 法制（OSS・各校セルフホストなので）

GDPR に「ソフトウェア作者」という役割は無く、あるのは controller と processor だけである。
**データに一度も触れない OSS 作者はどちらでもない。**

- 各校が controller。保持期間も消去請求への対応もデータ所在地も、デプロイした学校が決める
- 作者の責務は**「準拠を不可能にしないこと」だけ**で、これは既に満たしている —
  `deleteStudent` からカスケードで物理削除が通り、`DeletedRecord`（時刻を無視する
  永久 kill-list）は廃止済みなので、識別子が消えずに残る構造が無い
